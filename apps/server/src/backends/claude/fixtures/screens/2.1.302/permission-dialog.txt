⏺ File permissions matter because they are the primary mechanism by which an operating system
  decides who may read, modify, or execute a given file. Without them, any process running under any
  account could silently inspect credentials, overwrite configuration, or replace a trusted binary
  with malicious code. Permissions encode three separate questions for each file: who the owner is,
  which group may access it, and what everyone else is allowed to do. On Unix-like systems these are
  expressed as read, write, and execute bits, and they apply independently to files and
  directories. Directory permissions deserve particular attention, since the write bit on a
  directory controls whether entries can be created or removed, which is a different power from
  writing a file's contents. Getting permissions wrong is a common cause of real incidents: a
  world-readable private key, a world-writable script that cron later executes, or an
  over-privileged service account that turns a small bug into full compromise. The principle of
  least privilege says each file should grant the narrowest access that still lets its legitimate
  users do their work. Good defaults, careful umask settings, and periodic audits of unusual modes
  all reduce the blast radius of mistakes. Permissions are not a formality; they are a boundary.
