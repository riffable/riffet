  What a Resilient Job Queue Needs

  A job queue is easy to write and hard to make trustworthy. The naive version — push a job ID into
  Redis, pop it in a worker — works until the first worker crashes mid-job, at which point the job
  is silently gone or silently duplicated. Resilience comes from making the queue's state explicit
  and recoverable at every step.

  Four properties carry most of the weight:

  - At-least-once delivery with idempotent handlers. The queue should re-deliver on failure, and
    every handler must tolerate receiving the same job twice. Exactly-once is a promise distributed
    systems rarely keep; idempotency is the promise you can actually enforce.
  - Visibility timeouts and heartbeats. A popped job is reserved, not deleted. If the worker dies,
    the reservation expires and the job returns to the queue. Long-running jobs renew a heartbeat so
    they aren't reclaimed while still working.
  - Bounded retries with backoff and a dead-letter path. Retries should be capped, spaced with
    exponential backoff plus jitter, and terminal failures routed to a dead-letter queue where they
    can be inspected rather than lost.
  - Observability from the start. Queue depth, age of oldest job, retry counts, and failure rates
    need to be visible. Without them, a stalled consumer looks identical to a healthy one.

  type Job<T> = { id: string; payload: T; attempts: number };

  async function process<T>(job: Job<T>, run: (p: T) => Promise<void>) {
    if (job.attempts >= 5) return deadLetter(job);
    await run(job.payload); // handler must be idempotent
  }

  Build these in from day one. Retrofitting reliability onto a queue that already drops jobs is far
  harder than designing for it.
