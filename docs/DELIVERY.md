# 消息投递：主流程契约与可靠性设计

日期：2026-11-12。状态：阶段 0 实施中。

一条消息从输入框到 CLI 的完整路径：排队、准备、写入终端、确认送达、回合运行、回合结束。本文为这条路径定义状态、推进方、时间预算和失败去向，作为服务端、各后端和客户端共同遵守的契约。具体后端的协议细节见 [STEER.md](STEER.md)、[TERMINAL.md](TERMINAL.md)、[SESSION-JOURNAL.md](SESSION-JOURNAL.md)。

## 1. 问题

现有实现只保证安全，没有保证活性。

- **安全**：不重发、不在 CLI 忙时插入、不向未确认的界面按键。投递状态机（`Run.native.delivery`）、放行规则（`native/lane.ts`）和写入栅栏（`commitDispatchFence`）共同保证这一点。2026-11-11 的故障中没有一次重复发送或误投，这部分有效。
- **活性**：系统没有任何机制保证状态在有限时间内前进。Riffet 从三个有损渠道推断 CLI 状态：转录文件、hook、终端画面。任一渠道漏报或晚到，推断就停在"没看到"，系统再把"没看到"当成"没发生"。各处实现给出的去向不一致，有的立即放弃且不再追踪，有的无限阻塞且不提示原因，有的静默重试几十次。

此外，主流程依赖 0.25～2.5 s 的固定判定窗口，而服务端事件循环在 2026-11-11 有 49 次超过 1 s 的阻塞，8 次超过 3 s。固定窗口在这种负载下必然误判。

## 2. 不变量

安全（保持不变）：

- **S1 至多一次**：一条消息写入 CLI 至多一次。超时、重启、收敛（第 6 节）都不触发重写。
- **S2 按键前置条件**：回车只在输入框显示的就是本条消息时按下。
- **S3 回合隔离**：CLI 仍在运行上一条执行时，不放行下一条。

活性（新增）：

- **L1 有界前进**：每个非终态都有推进方、前进信号和时间预算。预算耗尽时进入确定的下一状态，不停留在原状态。
- **L2 阻塞可见**：队列被阻塞时，客户端拿到的阻塞原因与真实原因一致，并附带用户可执行的操作。调度器不对已知会失败的条件做重试。
- **L3 推断收敛**：派生状态（转录、hook 推断）与观测状态（终端画面、进程）持续不一致时，按第 6 节的优先级收敛，并记录一条诊断。
- **L4 等待抗阻塞**：等待外部进程的条件时，截止后必做一次终检；超时只改变显示和下一步，不丢弃追踪状态。

## 3. 投递状态机

| 状态 | 推进方 | 前进信号 | 时间预算 | 预算耗尽后 | 界面 |
| --- | --- | --- | --- | --- | --- |
| `queued` | 调度器 | 放行规则无阻塞 | 阻塞期间不计时，阻塞原因必须可见（第 4 节） | — | 排队中，附阻塞原因 |
| `preparing` | 调度器 + 后端 | 运行时就绪，写入栅栏提交 | CLI 拒收（`CLI_BUSY`）累计 3 min；等后台任务结束不计入 | `failed`：终端未就绪 | 发送中 |
| `dispatching` / `input_sent` | 后端 | 转录回显，或 hook 带上命令 ID | 后端回执窗口（Claude 90 s）；CLI 忙时不计时 | `uncertain`，后端继续在迟到窗口内收回执 | 发送中 |
| `observed` | 后端 | 回合结束记录 | 无。空闲状态持续 15 s / 60 s 后由空闲收敛关闭 | 关闭为结果未知 | 运行中 |
| `uncertain` | 用户 | 迟到回执（自动），或用户执行"检查状态"/"继续" | 迟到回执窗口（Claude 30 s、120 s 两次复查） | 保持，阻塞队列，等用户处理 | 暂时无法确认是否已发送，附操作 |
| `failed` / `cancelled` | — | 终态 | — | — | 发送失败 / 已取消 |

规则：

1. **写入后的阶段内部有子阶段**。以 Claude 为例：粘贴、输入框显示本条、按回车、回执。子阶段超时只把工作交给下一个子阶段，不退出 `input_sent`。比如粘贴后输入框迟迟不显示，就交给回执阶段继续观察输入框，显示出本条时再按回车。
2. **只有两种情况进入 `uncertain`**：回执窗口耗尽，或写入过程中 CLI 退出。进入后后端仍在迟到窗口内接收回执，收到就自动转为 `observed`。
3. **停止与发送的竞争**：用户在本条消息结果未定时停止，停止意图要保留到这次发送有结果为止。回执到达且回合已经开始，就中断这个回合，不让停止被静默吞掉。

## 4. 队列阻塞原因

`NativeStatus.queue.held.reason` 是客户端与调度器共用的唯一判定。

| 原因 | 解除条件 | 上限 | 用户操作 |
| --- | --- | --- | --- |
| `unconfirmed` | 迟到回执，或用户处理 | 无（需要人判断） | 检查状态 / 继续 |
| `turn_running` | 回合结束且无后台任务 | 无（等待是正常行为） | 停止 / 引导 |
| `attention` | 用户回答交互 | 无 | 回答 |
| `sending` / `steering` | 前一条有结果 | 回执窗口 | — |
| `stopping` / `recovering` / `workspace` | 对应操作完成 | 各自操作的预算 | — |
| `retrying` | 重试时间到 | `CLI_BUSY` 累计 3 min | — |

阶段 0 的补充：会话有待生效的配置切换（`configPending`，需要重启 CLI），而 CLI 还在运行回合或后台任务时，按 `turn_running` 阻塞，不再进入"放行、拒收、退回"的重试循环。阶段 1 把它拆成独立原因，并提供操作：停止后台任务并切换、本条不切换直接发送。

## 5. 等待原语

`apps/server/src/backends/shared/wait-for.ts` 提供 `waitFor(probe, options)`，所有等待外部进程的条件判断都用它：

- **终检**：截止后再执行一次探测。事件循环阻塞期间到达的 I/O，会在到期计时器之后才被处理；没有终检的等待会把"已经发生"误判成"超时"。
- **阻塞补偿**：一次轮询比预定间隔晚醒的部分计入补偿，截止时间相应后移，默认补偿上限等于窗口本身。
- **唤醒**：可以注册唤醒回调（hook 到达、状态变化），探测立即执行，不等下一个轮询点。
- **超时不等于失败**：返回 `undefined` 只表示窗口用完，下一步由调用方按第 3 节决定。

禁止的写法：`while (Date.now() < deadline)` 之后不做终检；`Promise.race(reply, timer)` 超时后删除用于匹配迟到回执的记录；超时后直接抛错而没有交接给下一阶段。阶段 1 加入静态检查，在 `apps/server/src/backends/**` 中拦截这些写法。

## 6. 状态收敛

派生状态来自转录和 hook 的推断。观测状态来自终端画面和进程，是 CLI 此刻实际显示和运行的样子。

| 事实 | 首选来源 | 收敛来源 | 收敛条件 |
| --- | --- | --- | --- |
| 进程存活 | 进程与 tmux | — | 不推断 |
| 回合进行中 | hook、转录的开始和结束记录 | 画面：空闲输入框、无忙碌指示 | 已有空闲收敛（`IDLE_RECONCILE_MS`） |
| 后台任务 | 转录的启动和结束报告、子 agent 元数据 | 画面：底部无任务入口、无 agent 列表 | 回合空闲、无发送和交互进行中、CLI 版本已验证，且连续 ≥ 5 s、≥ 2 次读屏一致 |
| CLI 自身队列 | 转录的 `queue-operation` 行 | 画面：空闲输入框、无忙碌指示 | 同上。空闲的 CLI 会立即处理队列，空闲且队列非空不是有效状态 |
| 消息已提交 | 转录回显 | 画面：输入框不再持有本条 | 只用于决定是否补按回车，不作为回执 |

规则：

1. 收敛只在派生状态声称"有事在做"、观测状态显示"空闲"时生效，方向永远是解除阻塞。反方向（画面显示忙）沿用现有判断，不由收敛改写。
2. 每次收敛输出一行结构化日志（会话、事实、派生值、观测值）。一次收敛说明有一个推断漏洞：修漏洞的同时保留收敛规则，二者都要有。
3. 未验证的 CLI 版本不做画面收敛，避免误读未采集过的界面。

## 7. 运行时健康

时间判断依赖事件循环及时运行。现状（2026-11-11）：71 次阻塞，49 次 ≥ 1 s，8 次 ≥ 3 s。profile 中主要是同步原生调用和子进程创建；数据库 5.3 GB，其中 `journal_events` 2.3 GB、`timeline_rows` 1.3 GB。

目标：p99 阻塞 < 250 ms，单次阻塞 < 1 s。手段：大事务分批执行；进程表扫描（`ps`、`lsof`、`pgrep`）去重并缓存；大文件解析分片让出主线程；数据库按保留策略压缩。`loop-health.ts` 的阻塞计数作为验收指标。

## 8. 故障模型与验证

按 [AGENTS.md](../AGENTS.md#测试与验证)，只为故障恢复和并发一致性补测试，每类故障一个代表用例，放在最接近行为边界的一层：

| 故障 | 期望 |
| --- | --- |
| 粘贴后输入框 > 2 s 才显示 | 显示后补按回车，转为 `observed`，不进入 `uncertain` |
| 等待期间事件循环阻塞超过窗口 | 终检读到已满足的条件 |
| 后台子 agent 被 `TaskStop` 停止，报告挂在恢复它的 `SendMessage` 调用上 | 后台任务清空，配置切换生效 |
| 结束报告完全丢失 | 画面收敛在设定时间后解除阻塞，并记录诊断 |
| `dequeue` 取出的不是最早一项（消息优先于任务报告） | 按优先级记账；仍有残留时由画面收敛清空 |
| 停止与刚提交的消息竞争 | 回合被中断，或回合从未开始 |
| RPC 回执超时后回显迟到 | 迟到回显仍能确认这条消息 |

## 9. 实施阶段

**阶段 0：止血。**

- 等待原语。
- Claude 后端：粘贴显示迟到交接给回执阶段；停止意图保留到发送有结果；`waitUntil` 终检；子 agent 结束报告识别（含 `SendMessage` 恢复）；CLI 队列按优先级记账；后台任务和 CLI 队列的画面收敛。
- 调度器：配置切换等后台任务时阻塞，不再重试。
- Cursor 提交终检与补按回车；终端扫描不丢弃已完成的结果；Droid 回执超时后保留命令对应关系；Pi 回执超时不杀进程（若安全上允许）。

**阶段 1：契约落地。** 独立的配置切换阻塞原因及客户端操作；等待写法的静态检查；Codex `/compact` 回执与终端端点检查改用等待原语（与进行中的 Codex 改动错开）；客户端提示去抖，同一原因不重复弹出。

**阶段 2：收敛全覆盖。** 回合状态、输入框、交互对话框的收敛规则扩展到 Codex 和 Cursor；第 8 节的故障注入用例。

**阶段 3：运行时健康。** 第 7 节的目标与数据库保留策略。

**指标**：`uncertain` 占比；各阻塞原因的时长分布；收敛次数（按事实分类）；事件循环阻塞次数。指标汇总在运行时统计中，回归时对比。
