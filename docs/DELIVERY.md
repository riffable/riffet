# 消息投递：主流程契约与可靠性设计

日期：2026-11-12。状态：阶段 0 实施中。

一条消息从输入框到 CLI 的完整路径：排队、准备、写入终端、确认送达、回合运行、回合结束。本文为这条路径定义状态、推进方、时间预算和失败去向，作为服务端、各后端和客户端共同遵守的契约。具体后端的协议细节见 [STEER.md](STEER.md)、[TERMINAL.md](TERMINAL.md)、[SESSION-JOURNAL.md](SESSION-JOURNAL.md)。

## 1. 问题

现有实现只保证安全，没有保证活性。

- **安全**：不重发、不在 CLI 忙时插入、不向未确认的界面按键。投递状态机（`Run.native.delivery`）、放行规则（`native/lane.ts`）和写入栅栏（`commitDispatchFence`）共同保证这一点。2026-11-11 的故障中没有一次重复发送或误投，这部分有效。
- **活性**：系统没有任何机制保证状态在有限时间内前进。Riffet 从三个有损渠道推断 CLI 状态：转录文件、hook、终端画面。任一渠道漏报或晚到，推断就停在"没看到"，系统再把"没看到"当成"没发生"。各处实现给出的去向不一致，有的立即放弃且不再追踪，有的无限阻塞且不提示原因，有的静默重试几十次。

此外，主流程依赖 0.25～2.5 s 的固定判定窗口，而服务端事件循环在 2026-11-11 有 49 次超过 1 s 的阻塞，8 次超过 3 s。固定窗口在这种负载下必然误判。

## 2. 不变量

安全（保持不变）：

- **S1 至多一次**：一条消息写入 CLI 至多一次。超时、重启、收敛（第 6 节）都不触发重写。
- **S2 按键前置条件**：回车只在输入框显示的就是本条消息时按下。
- **S3 回合隔离**：CLI 仍在运行上一条执行时，不放行下一条。

活性（新增）：

- **L1 有界前进**：每个非终态都有推进方、前进信号和时间预算。预算耗尽时进入确定的下一状态，不停留在原状态。
- **L2 阻塞可见**：队列被阻塞时，客户端拿到的阻塞原因与真实原因一致，并附带用户可执行的操作。调度器不对已知会失败的条件做重试。
- **L3 推断收敛**：派生状态（转录、hook 推断）与观测状态（终端画面、进程）持续不一致时，按第 6 节的优先级收敛，并记录一条诊断。
- **L4 等待抗阻塞**：等待外部进程的条件时，截止后必做一次终检；超时只改变显示和下一步，不丢弃追踪状态。

## 3. 投递状态机

| 状态 | 推进方 | 前进信号 | 时间预算 | 预算耗尽后 | 界面 |
| --- | --- | --- | --- | --- | --- |
| `queued` | 调度器 | 放行规则无阻塞 | 阻塞期间不计时，阻塞原因必须可见（第 4 节） | — | 排队中，附阻塞原因 |
| `preparing` | 调度器 + 后端 | 运行时就绪，写入栅栏提交 | CLI 拒收（`CLI_BUSY`）累计 3 min；等后台任务结束不计入 | `failed`：终端未就绪 | 发送中 |
| `dispatching` / `input_sent` | 后端 | 转录回显，或 hook 带上命令 ID | 后端回执窗口（Claude 90 s）；CLI 忙时不计时 | `uncertain`，后端继续在迟到窗口内收回执 | 发送中 |
| `observed` | 后端 | 回合结束记录 | 无。空闲状态持续 15 s / 60 s 后由空闲收敛关闭 | 关闭为结果未知 | 运行中 |
| `uncertain` | 用户 | 迟到回执（自动），或用户执行"检查状态"/"继续" | 迟到回执窗口（Claude 30 s、120 s 两次复查） | 保持，阻塞队列，等用户处理 | 暂时无法确认是否已发送，附操作 |
| `failed` / `cancelled` | — | 终态 | — | — | 发送失败 / 已取消 |

规则：

1. **写入后的阶段内部有子阶段**。以 Claude 为例：粘贴、输入框显示本条、按回车、回执。子阶段超时只把工作交给下一个子阶段，不退出 `input_sent`。比如粘贴后输入框迟迟不显示，就交给回执阶段继续观察输入框，显示出本条时再按回车。
2. **只有两种情况进入 `uncertain`**：回执窗口耗尽，或写入过程中 CLI 退出。进入后后端仍在迟到窗口内接收回执，收到就自动转为 `observed`。
3. **停止与发送的竞争**：用户在本条消息结果未定时停止，停止意图要保留到这次发送有结果为止。回执到达且回合已经开始，就中断这个回合，不让停止被静默吞掉。

## 4. 队列阻塞原因

`NativeStatus.queue.held.reason` 是客户端与调度器共用的唯一判定。

| 原因 | 解除条件 | 上限 | 用户操作 |
| --- | --- | --- | --- |
| `unconfirmed` | 迟到回执，或用户处理 | 无（需要人判断） | 检查状态 / 继续 |
| `turn_running` | 回合结束且无后台任务 | 无（等待是正常行为） | 停止 / 引导 |
| `attention` | 用户回答交互 | 无 | 回答 |
| `sending` / `steering` | 前一条有结果 | 回执窗口 | — |
| `stopping` / `recovering` / `workspace` | 对应操作完成 | 各自操作的预算 | — |
| `retrying` | 重试时间到 | `CLI_BUSY` 累计 3 min | — |

阶段 0 的补充：会话有待生效的配置切换（`configPending`，需要重启 CLI），而 CLI 还在运行回合或后台任务时，按 `turn_running` 阻塞，不再进入"放行、拒收、退回"的重试循环。阶段 1 把它拆成独立原因，并提供操作：停止后台任务并切换、本条不切换直接发送。

## 5. 等待原语

`apps/server/src/backends/shared/wait-for.ts` 提供 `waitFor(probe, options)`，所有等待外部进程的条件判断都用它：

- **终检**：截止后再执行一次探测。事件循环阻塞期间到达的 I/O，会在到期计时器之后才被处理；没有终检的等待会把"已经发生"误判成"超时"。
- **阻塞补偿**：一次轮询比预定间隔晚醒的部分计入补偿，截止时间相应后移，默认补偿上限等于窗口本身。
- **唤醒**：可以注册唤醒回调（hook 到达、状态变化），探测立即执行，不等下一个轮询点。
- **超时不等于失败**：返回 `undefined` 只表示窗口用完，下一步由调用方按第 3 节决定。

禁止的写法：`while (Date.now() < deadline)` 之后不做终检；`Promise.race(reply, timer)` 超时后删除用于匹配迟到回执的记录；超时后直接抛错而没有交接给下一阶段。阶段 1 加入静态检查，在 `apps/server/src/backends/**` 中拦截这些写法。

## 6. 状态收敛

派生状态来自转录和 hook 的推断。观测状态来自终端画面和进程，是 CLI 此刻实际显示和运行的样子。

| 事实 | 首选来源 | 收敛来源 | 收敛条件 |
| --- | --- | --- | --- |
| 进程存活 | 进程与 tmux | — | 不推断 |
| 回合进行中 | hook、转录的开始和结束记录 | 画面：空闲输入框、无忙碌指示 | 已有空闲收敛（`IDLE_RECONCILE_MS`） |
| 后台任务 | 转录的启动和结束报告、子 agent 元数据 | 画面：底部无任务入口、无 agent 列表 | 回合空闲、无发送和交互进行中、CLI 版本已验证，且连续 ≥ 5 s、≥ 2 次读屏一致 |
| CLI 自身队列 | 转录的 `queue-operation` 行 | 画面：空闲输入框、无忙碌指示 | 同上。空闲的 CLI 会立即处理队列，空闲且队列非空不是有效状态 |
| 消息已提交 | 转录回显 | 画面：输入框不再持有本条 | 只用于决定是否补按回车，不作为回执 |

规则：

1. 收敛只在派生状态声称"有事在做"、观测状态显示"空闲"时生效，方向永远是解除阻塞。反方向（画面显示忙）沿用现有判断，不由收敛改写。
2. 每次收敛输出一行结构化日志（会话、事实、派生值、观测值）。一次收敛说明有一个推断漏洞：修漏洞的同时保留收敛规则，二者都要有。
3. 未验证的 CLI 版本不做画面收敛，避免误读未采集过的界面。
4. 画面否定匹配（未命中忙碌规则）只说明「未识别出忙碌」，不得作为跳过控制动作或伪造终态的依据。实时开启的回合执行停止时，必须按回合状态发出中断信号（如 `C-c`），不因画面看似空闲而跳过；只有冷重启回放且确认非忙碌的回合才可跳过。

### 状态正交分层与因果单调性

会话状态由四条正交轴组成，分别回答不同问题，互不覆盖：

1. **进程与连接（Runtime）**：`offline | starting | ready | conflict | failed`（CLI 或 app-server 是否存活并已建立控制连接）。
2. **消息投递（Delivery，按 `Run`）**：`submitting → queued → preparing → dispatching → input_sent → observed | uncertain | failed | cancelled`（用户消息是否已送达 CLI）。
3. **前台主回合（Foreground Turn）**：`idle | busy | compacting | attention | stopping`（主 Agent 当前是否在执行本轮任务）。
4. **后台委派（Background）**：主回合结束后仍在运行的子 Agent、工作流与后台 shell，独立于前台回合结算。

为避免跨通道（`status`、`run`、`rows`）异步到达时出现「Agent 输出已上屏但状态仍为空闲/已处理」或「气泡仍显示发送中而回答已流式输出」的逆序现象，服务端与四端共同遵守三条**因果单调性（Causal Monotonicity）**不变量：

- **C1（投递与处理的阶段交接）**：真正排队等待前序回合的消息只出现在输入框上方的 `ComposerDock`；已进入正文的 `queued / preparing / dispatching / input_sent`（未收件且无输出）消息处于投递阶段，气泡下方显示「发送中」（或「恢复中」）。一旦收件确认（`observed` / `run.state === 'running'`）或本轮产生输出，气泡下方切回时间戳，同帧由底部 `WorkingIndicator`（「正在处理」）与 `TurnProcess`（「处理中 · Xs」）接管。
- **C2（状态先于或随同转写发出）**：
  - 新建会话在 `setNativeSessionId` 绑定原生会话 ID 时立即挂载驱动的实时控制订阅，不留首连空窗；
  - 各后端运行时（Claude `readTranscript`、Codex `onNotification`、Cursor `refreshParentTranscript` 与 `updateStatus`）在观测到新回合开始或未完结输出时，先推进并广播 `phase: 'busy'`，再唤醒转写拉取；Cursor TUI 尚未绘出底栏（`booting`）但已有流式步骤或未回答提示时，按 `busy` 报告而不被 `starting` 遮蔽。
- **C3（输出隐含收件与运行）**：
  - 同一回合内只要已有非用户输出行（`thought`、`tool`、`assistant`）跟随在用户消息之后，即视为 CLI 已收件，气泡下不再显示「发送中」；
  - 在 `analyzeTimelineTurns` 与客户端 `working` 判定中，已跨过派发边界（`dispatching / input_sent / observed`）或已有同轮输出的未完结 `Run`（含尚未收到 `run_updated` 微任务的 `queued` 状态）直接归入 `activeTurns` 并激活会话工作态，保证 `TurnProcess` 首帧即为「处理中」。

### 回合结束与更正

- 工具失败、可重试的响应断流、线程级错误和静默时长本身都不证明回合结束。Claude 的 `isApiErrorMessage` 携带 `stop_reason: tool_use` 时仍属于运行中的回合；子 agent 静默时保留运行状态，直到明确结束、停止或宿主退出。
- 停止必须由正向信号确认（hook `Stop`、转录中断记录、进程退出，或发出中断信号后画面稳定回到可输入态）；未获确认时保持运行态、恢复已撤下的活跃回合记录并返回未确认错误，不写入合成 `cancelled`。
- Claude 实时状态与 journal 共用结束规则：未被阻止的 Stop 汇总可以结束回合，不必再等 `turn_duration`；Stop hook 反馈或追加上下文让原回合继续。子 agent 的终止 API 错误记为失败。
- 结束通知只清理它所对应的回合。Droid 的旧结束通知不能清掉已经回显的新回合；Codex / Traex 的线程 idle 或 systemError 不能替代仍未结束回合自己的结果。
- 同一 native session、同一 turn 的明确撤回可以更正之前的 provider failure / completion。撤回和新结果持久化后，重启仍能补齐 Run 状态；普通迟到输出、旧版本结果、用户停止和已释放的跟踪不触发恢复，消息不重发。
- 旧 Claude cursor 首次读取时校验已读记录，只修正能与原始错误时间、内容和后续回合对应的误判；修正、内容归属和 cursor 一起提交，保留日志 generation。停止过的续接回合不自动合并。

## 7. 运行时健康

时间判断依赖事件循环及时运行。现状（2026-11-11）：71 次阻塞，49 次 ≥ 1 s，8 次 ≥ 3 s。profile 中主要是同步原生调用和子进程创建；数据库 5.3 GB，其中 `journal_events` 2.3 GB、`timeline_rows` 1.3 GB。

目标：p99 阻塞 < 250 ms，单次阻塞 < 1 s。手段：大事务分批执行；进程表扫描（`ps`、`lsof`、`pgrep`）去重并缓存；大文件解析分片让出主线程；数据库按保留策略压缩。`loop-health.ts` 的阻塞计数作为验收指标。

2026-11-12 的三份阻塞 profile（各 30 s）按主线程自耗时排序：

| 来源 | 每 30 s 自耗时 | 说明 |
| --- | --- | --- |
| `execFile` 超时后的 `kill` | 最高 7.6 s，单次最长 2.2 s | 循环一旦被堵，到期的超时定时器逐个执行 `kill`，越堵越久 |
| 创建子进程（`spawn`） | 0.8～3.5 s，200～430 次 | 几乎全部来自终端服务：读屏、`inspectPane` 的 `tmux`、`pgrep`、`ps`、`lsof` |
| SQLite 提交 | 一次 1.0 s | 时间线折叠的提交越过 WAL 页数上限，在提交内做检查点 |
| 停止 CPU profile | 0.8 s | 诊断自身；每小时至多一次 |
| SQLite 读、转录解析 | 各 0.4～0.9 s | 分散，单次不长 |

已处理：

- 一次性命令经 `exec.ts` 在 worker 线程里执行，创建和杀进程不再占用事件循环。终端服务的 `tmux`、`pgrep`、`ps`、`lsof` 都走这里；新增这类调用时不要直接用 `execFile`。
- WAL 检查点由 `wal-checkpoint.ts` 的 worker 线程用自己的连接做（PASSIVE，不等待读写方）；服务连接的自动检查点上限调到 20000 页作为兜底，worker 退出时恢复默认值。
- 阻塞 profile 的采样间隔改为 4 ms。

未处理：`store.listSessions()` 每次解析全部会话；折叠与转录解析仍在主线程。部署上面三项后以 `loop-health` 的数字决定是否需要把它们移出主线程。

## 8. 重启

服务重启只结束随服务一起退出的进程。Claude、Cursor 跑在 Riffet 自己的 tmux 里，Codex、Traex 跑在脱离服务的 app-server 守护进程里，重启后回合照常进行（后端特征 `survivesRestart`）；Droid、Pi、DSH（子进程、桥接）和 chat（进程内）随服务结束。

- **能否重启**：`GET /api/service/restartable` 返回能否重启及阻塞的会话（会话、标题、后端、原因）。有消息处于 `preparing`、`dispatching`、`input_sent` 时不能重启，否则重启后这些消息会变成 `uncertain`。不随服务存活的后端有回合在跑、会话处于运行或等待状态、或有后台任务时，也不能重启。存活后端的 `observed` 回合不阻塞重启。
- **暂停派发**：`POST /api/service/drain {on, holder}`（`holder` 是调用方每次重启尝试自生成的 ID，各持各的租约，解除只撤销自己的；缺省为共用的旧持有者，服务只要还有未过期的租约就保持暂停）。暂停期间新消息照常接收并以 `queued` 持久化，但不派发，所以等待一定会结束；重启后自动发出。引导同样保持排队：解除暂停而没有重启时，照常投给它的回合；重启后转为下一条消息（与重启前未写入的引导相同）。这样引导在工具边界上的等待不会拖住重启。暂停只存在内存里，是一份 30 s 的租约，等待方每次轮询都会续期：重启会清除它，等待方中途退出时它也会在 30 s 内自行失效。
- **重启后收回**（`store.recoverInterruptedRuns`，按 `restartObservation` 冻结的后端清单）：`queued`/`preparing` 保持排队；`dispatching`/`input_sent` 记为 `uncertain`，不重发（S1）。Claude、Cursor 等待回合结束 hook 的 `observed` 回合继续观察：hook 在停机期间丢失时，Claude 由转录里的结束记录（`stop_hook_summary`、`turn_duration`）补上，否则空闲后关闭为结果未知。Codex、Traex 带回合 ID 的 `observed` 回合继续观察：调度器为每个未结束的回合打开观察，读回线程即得到停机期间结束的回合；读不到结果的同样按空闲收敛关闭。Cursor 正在流式输出的那一步草稿不保留，这一步写完后照常出现。
- **调用方**：`scripts/riffet-restart.sh`、`riffet restart` 与 `riffet update`（CLI、launchd、systemd 托管）先暂停派发，等到可以重启再停服；超时则解除暂停，列出阻塞的会话并按原样退出（脚本退出码 4）。脚本、`riffet restart` 与 `riffet update` 的 `--force`、`--wait-idle 0` 不等待直接重启；Mac App 的重启（设置与版本提示）每 2 s 轮询一次，列出阻塞的会话并可「仍然重启」或「取消」（解除暂停），3 分钟仍未就绪则解除暂停并报出这些会话。不支持这两个接口的旧服务退回原来的检查（`riffet update` 在有会话运行时拒绝更新）。

## 9. 故障模型与验证

按 [AGENTS.md](../AGENTS.md#测试与验证)，只为故障恢复和并发一致性补测试，每类故障一个代表用例，放在最接近行为边界的一层：

| 故障 | 期望 |
| --- | --- |
| 粘贴后输入框 > 2 s 才显示 | 显示后补按回车，转为 `observed`，不进入 `uncertain` |
| 等待期间事件循环阻塞超过窗口 | 终检读到已满足的条件 |
| 后台子 agent 被 `TaskStop` 停止，报告挂在恢复它的 `SendMessage` 调用上 | 后台任务清空，配置切换生效 |
| 结束报告完全丢失 | 画面收敛在设定时间后解除阻塞，并记录诊断 |
| `dequeue` 取出的不是最早一项（消息优先于任务报告） | 按优先级记账；仍有残留时由画面收敛清空 |
| 停止与刚提交的消息竞争 | 回合被中断，或回合从未开始 |
| RPC 回执超时后回显迟到 | 迟到回显仍能确认这条消息 |

## 10. 实施阶段

**阶段 0：止血。**

- 等待原语。
- Claude 后端：粘贴显示迟到交接给回执阶段；停止意图保留到发送有结果；`waitUntil` 终检；子 agent 结束报告识别（含 `SendMessage` 恢复）；CLI 队列按优先级记账；后台任务和 CLI 队列的画面收敛。
