# AI 友好工程机制（AIF）

返回 [中文 README](../../README.zh-CN.md)。

本文规定 Riffet 仓库如何降低 agent 理解、调试和修改代码的成本，并在长期迭代中保持这一水平。Riffet 的代码基本由 agent 编写，结构劣化的速度与提交速度同量级，所以本机制按反馈系统设计：持续采集信号，按信号调整规则、模块边界和机制自身，而不是一次性定好一套规则。数据截至 2026-11-19。

### 1.2 架构上的已知结构

- **客户端逻辑两套，界面四套**。Web 是 TypeScript；Mac、iOS 和 Android 通过 RiffetKit 共用 Kotlin 的同步、缓存与解码逻辑。时间线在服务端折叠（[同步协议 v3](../SYNC-V3.md)）。跨端成本主要在界面层，以及 TypeScript 与 Kotlin 两套逻辑之间。
- **Agent 后端八个，并且还在增加**。每个后端解析一到多条外部输入：终端屏幕、会话记录文件、App Server 协议、hook 事件、流式 JSON。外部 CLI 的行为随版本变化，是最大的隐式知识来源。
- **插件是对外平台**。插件 API 由 `gen:plugin-api` 管理发布形态，内部插件在仓库外维护。为插件编写代码的 agent 同样是这套机制的使用者。
- **多个 agent 会话同时在同一工作区的 main 上修改**。任何基于 `git diff` 的改动范围都会混入其他会话的改动。

### 1.3 已有的约束

- `AGENTS.md` 分根目录与各端两层。
- 11 个 `check:*` 脚本；`check:layers`、`check:design`、`check:perf` 带只减不增的基线。
- 14 个生成物由 `gen:*:check` 校验；`gen:contracts` 从 TypeScript 生成 Kotlin 契约；`gen:timeline-fixtures` 生成同步契约的测试数据，Kotlin 解码器用它测试。
- 录制与回放：Claude 屏幕解析有两个 CLI 版本的录制数据（`apps/server/src/backends/claude/fixtures/screens/`）；移动端终端引擎用 tmux 录制流做一致性测试（`scripts/record-terminal-fixtures.ts`）；Web 转录可录制同步流并在无头浏览器回放（`scripts/replay-transcript.ts`）。
- 排障：`riffet doctor --json`、`riffet logs --scope --json`，以及 `scripts/` 下的 `probe-*` 端到端探针。

### 1.4 问题

| 成本 | 问题 |
|---|---|
| 理解 | 知识按功能写在 `docs/` 下 47 份平铺文档里，代码按目录组织，两者之间没有索引。agent 靠搜索拼出改动范围内的规则。热点文件过大，读一次就占满有效上下文。 |
| 调试 | 只有 Claude 屏幕解析有录制数据；Codex、Cursor 等后端复现只能接真实 CLI。排障结论留在会话里，没有回到仓库。 |
| 开发 | 「改 A 必须同时改 B」的规则只写在文档里（如根 `AGENTS.md` 的预热键）。该跑哪些检查靠读 `AGENTS.md` 的对照表。同一功能的界面分布在四端，漏改要到实机才发现。 |
| 演进 | 规则只增不减，根 `AGENTS.md` 和各类文档持续变长；没有信号说明哪条规则有效、哪条已经过时；模块边界一旦划定就没有复核时机。 |

## 2. 目标与度量

agent 接到任务后：

1. 用一条命令拿到本次改动范围内的规则、同改项和验证命令，输出有长度上限；
2. 涉及外部 CLI 行为时，能用录制数据在本地确定性复现；
3. 改完用一条命令跑完该跑的检查，漏掉的同改项被检查拦下；
4. 单个模块能在一次阅读内读完入口和直接依赖。

机制本身：

5. 每次修复都能归到一类缺失的知识或检查，归类结果驱动机制调整；
6. 规则、知识条目和模块边界都有复核与退役的路径。

度量按模块统计，只看趋势，不合成总分，也不设为合入门槛（指标一旦成为门槛就会被优化成数字本身）：

| 指标 | 定义 | 数据源 |
|---|---|---|
| 首次编辑前调用数 | 回合内第一次修改文件之前的工具调用数 | `workbench.db` 的 `tool_calls`，按回合排序 |
| 验证失败数 | 回合内失败的命令调用数 | `tool_calls.failed` |
| 返工率 | 30 天内触及该模块的提交中 fix 的占比 | git |
| 修复归因分布 | fix 提交按缺失类型的分布（§5.6） | 提交尾注 |
| 跨端遗漏 | 归因为「跨端」的 fix 数 | 同上 |
| 外部行为覆盖 | 场景 × 后端 × CLI 版本矩阵中有录制数据的格数（§5.4） | 录制目录 |
| 热点 | 30 天改动次数 × 文件行数，取前 20 | git |

`tool_calls` 目前只有工具名和失败标记。按模块归因需要每次调用的目标路径，阶段 2 从 journal 的工具行取，取不到时在写入侧补字段。这些数据只在本机，外部贡献者没有；机制的拦截部分不依赖它们。

## 3. 设计原则

1. **推导优先于声明**。模块范围、依赖、同改关系、热点都能从目录、导入关系和 git 历史算出，只声明算不出的意图：层级、允许的依赖、不变量。手写的映射本身就是会过期的隐式知识。
2. **声明与代码放在一起**。模块的声明和文档放在模块目录里，随代码移动、重命名和删除；全局视图由脚本生成，不手写。
3. **知识的落点按可靠程度选择**：从结构上消除，好于从单一来源生成，好于检查拦截，好于写进模块文档，好于写进全局文档。
4. **在接口处验证一致性**。跨实现的一致性（八个后端、两套客户端逻辑）用一套共享场景在接口处验证，不在每个实现里各写一份。
5. **闭环**。每次修复记录缺了什么；规则记录触发次数；按这些信号升级、降级或删除规则，复核模块边界。
6. **机制自身有预算**。agent 上下文有限，分发给 agent 的内容有长度上限；新增一条规则时，说明它替代或淘汰了什么。
7. **只减不增**：现存超标进基线，新改动不能让基线上升，不做一次性全量改造。
8. **与具体 agent、具体仓库无关**。机制由仓库文件和命令组成，任何 agent 读到的都是同一份；引擎不写死 Riffet 的目录，插件仓库也能使用。Riffet 自身的会话能力只用来加速。

## 4. 结构

机制分三条回路，时间尺度不同：

| 回路 | 时机 | 输入 | 动作 | 输出 |
|---|---|---|---|---|
| 改动回路 | agent 修改期间，秒级 | 本会话改动的文件 | 分发模块上下文；运行受影响的检查与测试 | 上下文、检查结果 |
| 提交回路 | 提交与 CI | 提交内容与尾注 | 全量检查；校验 fix 尾注；校验录制数据 | 合入或拦截；归因记录 |
| 演进回路 | 每周，由 Riffet 自动化执行 | git 历史、`workbench.db`、最新版本 CLI 的实测结果 | 生成报告；挖掘变更耦合；检测 CLI 漂移；列出待复核的规则、条目与边界 | 改造优先级与机制调整项，由人确认后执行 |

改动回路和提交回路是确定性的，决定能否合入；演进回路只产出建议，不自动修改规则或代码。

## 5. 组成

### 5.1 模块

**范围由目录推导**。默认每个含模块文档的目录是一个模块，范围是该目录减去其中更深的模块。服务端的层级只在 `scripts/check-layers.mjs` 的 `LAYERS` 里声明一处，`aif` 读取它得出模块所在的层，模块文档不再重复声明（写了 `layer` 会被 `check:modules` 拦下）。

**声明写在模块文档的头部**。每个模块根目录放一份 `AGENTS.md`，头部是机器读取的声明，正文是给 agent 的知识。一个文件同时承担两种职责，避免声明与说明分离后不同步：

<!-- doc-paths:off -->
```markdown
---
module: server.backends.codex
recordings: fixtures
verify:
  - npx vitest run apps/server/src/backends/codex
co-change:
  - when: launch.ts#warmKey
    with: [apps/server/src/backends/claude/warm.ts#claudeWarmKey]
    reason: 影响启动的会话字段要同时进各 Agent 的预热键
---

## 职责
……
```
<!-- doc-paths:on -->

正文固定五节：

| 节 | 内容 |
|---|---|
| 职责 | 一句话 |
| 入口 | 读这个模块从哪几个文件开始 |
| 不变量 | 改动时不能破坏的约束 |
| 外部行为 | 依赖的 CLI 行为，每条对应一个录制场景（§5.4） |
| 排障 | 症状 → 先看哪里：日志 scope、数据库表、回放命令 |

正文不超过 80 行；不写目录地图和实现过程。`docs/` 下的功能文档继续记录设计和原因，并链接到相关模块。

**全局视图按需计算，不提交生成物**。`pnpm aif modules` 扫描所有模块文档列出模块与层级，`check:modules`、`aif context` 和报告每次运行时同样现场计算。扫描只需几十毫秒，提交一份索引只会多一个需要同步的文件。

`check:modules` 检查：

- 声明合法：`module` 唯一，正文恰好是上述五节且不超过 80 行，`verify` 引用的脚本和路径存在；
- 锚点存在：正文和 `co-change` 中的 `文件#符号` 指向的文件存在、符号出现在文件里；正文里反引号括起的源文件路径和以 `/` 结尾的目录也必须存在；
- 单文件行数上限 800 行（不含测试与录制数据），现存超限记在 `scripts/aif-baseline.json`，只减不增（`--update` 降低基线，`--update --add <路径>` 登记新的超限文件）；
- 待实现（阶段 1 与阶段 3）：每个源文件都属于某个模块；跨模块导入只指向声明的模块。服务端的导入继续由 `check:layers` 按 `LAYERS` 约束。

### 5.2 依赖与变更耦合

- **导入依赖**从代码解析，不手写。
- **变更耦合**从 git 历史挖掘：两个文件在多个提交里同时被修改，而它们之间没有导入关系，就说明存在隐式依赖。演进回路每周计算一次，结果分三种处理：
  - 同一模块内的耦合：不处理；
  - 跨模块、有明确原因的耦合（如各后端的预热键）：先尝试从结构上消除，消除不了的写成同改规则；
  - 跨模块、找不到原因的高频耦合：列为边界复核项，说明模块切分可能不对。
- **同改规则**写在模块文档头部的 `co-change`：`when` 是触发的文件或符号，`with` 是必须一起检查的文件，`reason` 是原因。`when` 带符号时，只有改动的行或所在函数涉及该符号才触发。改动命中而 `with` 都没动时，`aif context` 列出提醒，`verify` 给出警告。用警告而不拦截，是因为改到 `when` 不一定要改 `with`；规则能精确表达时，应当从结构上消除，而不是升级成拦截。规则的来源是变更耦合的挖掘结果或一次归因为「同改」的修复，不凭印象添加。

预热键是第一个要从结构上消除的规则：Cursor `resourceKey`、Codex `warmKey`、Claude `claudeWarmKey` 改为从同一份启动字段列表派生，删除根 `AGENTS.md` 里对应的提醒。

### 5.3 知识条目的锚定与过期

模块文档的「不变量」「外部行为」「排障」中，每一条都锚定到具体的代码符号或录制场景，例如 `runtime.ts#settleTurn`。

- `check:modules` 校验锚点存在，与 `check:docs` 校验路径的做法一致（已实现）；
- （阶段 2）锚定的代码改动后，`aif context` 在该条目旁标出「锚点已改动，未复核」，agent 改到这里时顺带确认或更新；
- （阶段 2）180 天没有被 `aif context` 分发、锚点也没改动过的条目，列入演进回路的待删除项。

### 5.4 接口一致性测试

一致性在接口处用共享场景验证。场景只定义一次，各实现提供自己的录制数据或适配。

**Agent 驱动**。在驱动契约处定义场景目录：启动、流式输出、工具调用、权限请求、中断、恢复、子 agent、压缩、异常退出等。覆盖情况是一张「场景 × 后端 × CLI 版本」矩阵：

- **录制**：统一入口 `pnpm record <后端> <场景>`，合并现有 `probe-*-e2e` 与 `scripts/record-terminal-fixtures.ts` 的做法，保存原始输入和 CLI 版本，存放在 `apps/server/src/backends/<后端>/fixtures/<通道>/<CLI 版本>/`，沿用 Claude 屏幕录制的目录约定；
- **回放**：CI 只用录制数据，不接真实 CLI。断言的是驱动输出的会话行，不是解析的中间状态，以便重构解析代码时测试不变；
- **重录**：CLI 升级时用 `record` 重录，录制数据的差异作为代码评审的一部分；
- **漂移检测**：演进回路每周用本机最新版本的 CLI 跑一遍场景，与录制结果对比。有差异就提示重录或修改解析代码，这样在用户遇到问题之前就能发现；
- **新后端接入**：以填满矩阵为完成标准，不依赖接入者记得测什么；
- **修复规则**：修改解析逻辑的 fix 必须新增或更新录制数据。对声明了 `recordings` 的模块，fix 提交改了它的源码却没有改录制数据，且尾注缺失或为 `external` 时，CI 给出警告；尾注是其他类型时不警告，因为那类修复与 CLI 的输出无关。

按 `AGENTS.md`「测试与验证」，这类测试属于外部协议契约，在保留范围内。

**Codex 的实现**（`apps/server/src/backends/codex/recording.ts`）：

- 录制位置是 `CodexAppServerClient` 接口，不是 socket。`pnpm record codex <场景>` 用真实 CLI 驱动 `CodexBackendAdapter`，记录运行时发出的请求、收到的响应、通知、服务端请求及其答复。录制在这一层，生产代码不需要任何录制开关；
- 头信息记下 CLI 版本、`initialize` 返回的 userAgent 和 `probeAppServer` 的探测结果。回放时用同一份探测结果，使驱动走与录制时相同的启动路径；
- 回放按录制顺序送入消息：每条入站消息在它之前的那条出站消息被运行时重现之后送达，且只送达一次；响应之前到达的通知仍在响应之前送达。运行时安静超过 150 毫秒而仍有消息未送达（通常是它没有重发某个由定时器驱动的轮询），就按录制顺序放出下一批。录制里没有的请求，返回该方法最后一次的响应，没有则按未知方法报错。请求模式的变化因此体现为会话行的变化，而不是挂起；
- 服务端请求（审批）会送到运行时，但宿主还不能作答，需要审批的场景暂时无法录制，阶段 1 补上；
- 期望结果是规整后的会话行（去掉序号、摘要、时间和生成的 id），用 vitest 的文件快照存放在录制数据旁边，`-u` 更新；
- 仓库公开，录制时替换路径、用户名、主机名、URL、模型 id 和提供方名称，去掉账号、限额、服务等级、指令文件位置与提供方配置，userAgent 只保留版本号；丢弃描述本机环境的通知：用户自己的 hook、MCP 服务状态、账号、远程控制和提供方的审核元数据；账号与配置读取请求保留，答复置空，使回放走与录制相同的路径；
- CLI 只用于录制，`codex` 不在时回放照常运行。

当前覆盖：Codex App Server 在 0.167.2 上有三个场景（单回合回答、执行命令、两回合）；Codex 的 rollout 文件与 hook、Claude 的会话记录文件与 hook、其余后端都还没有录制；Claude 屏幕有两个版本。

**同步协议**。`gen:timeline-fixtures` 已为 Kotlin 解码器提供共享测试数据，扩展到 Web 的 TypeScript 消费方，使两套客户端逻辑用同一份数据测试。

**架构方向**。跨端成本与客户端里的逻辑量成正比。新的业务逻辑默认放在服务端或 `packages/`，Kotlin 共用逻辑放在 RiffetKit；四端界面层只做呈现和平台交互。时间线已在服务端折叠，是这个方向的先例。

**插件 API**。插件 SDK 随包附带面向 agent 的说明（扩展点、限制、示例），由 `gen:plugin-api` 同源生成。在插件仓库里工作的 agent 不需要读 Riffet 源码。

### 5.5 改动范围与分发

**改动范围按会话确定，不用 `git diff`**。工作区由多个会话共享，`git diff` 会混入其他会话的改动。范围的来源按优先级：

1. 显式传入的路径；
2. （阶段 2）在 Riffet 会话中运行时，由 Riffet 提供本会话写过的文件列表。前提是工具调用记录了目标路径，与 §2 的按模块归因是同一项改动；
3. 都没有时取工作区的全部改动，并在输出中提示范围可能混入其他会话的改动。

**两条命令**：

- `pnpm aif context [路径…]`：输出范围内的目录规则、模块文档正文、录制数据的覆盖（通道与 CLI 版本）、验证命令、命中的同改规则，以及未归属模块的源文件数。全部输出不超过约 2000 token：超出时模块正文依次缩短为条目列表、只留小节标题，同改提醒始终保留。未复核的条目（§5.3）与跨端位置在阶段 2、3 加入；
- `pnpm verify [路径…]`：运行范围内模块的 `verify`、命中的全局检查，以及 `vitest related` 选出的测试，`--dry-run` 只列出命令。CI 继续跑全量。全局检查的路径对应关系目前集中在 `scripts/aif.ts` 的 `GLOBAL_CHECKS`，取代了根 `AGENTS.md` 里的对照表；生成物检查不手写，从每个 `gen:*:check` 的脚本推导：脚本本身、它在 `scripts/` 里传递引用的文件、它引用的整个包，以及脚本里写明的仓库路径（输入与输出），改动命中其中之一就运行。

根 `AGENTS.md` 要求：开始修改前运行 `aif context`，提交前运行 `verify`。

**会话内注入（阶段 3，可选）**。Riffet 已经接收 Claude、Codex、Cursor 的 hook 事件，可以在 agent 第一次编辑某模块时，把该模块的 `aif context` 注入到会话里，agent 不再需要记得运行命令。这项能力对任何用户仓库都适用，按通用能力设计，不写死 Riffet 仓库。

### 5.6 修复归因

每个 fix 提交带一行尾注，说明是什么缺失导致了这个问题：

<!-- doc-paths:off -->
```
Missed: context | co-change | external | invariant | cross-platform | logic
```
<!-- doc-paths:on -->

| 值 | 含义 | 机制上的对应动作 |
|---|---|---|
| `context` | 相关知识存在于仓库某处，但没有分发给改动者 | 调整模块范围或 `aif context` 的选取 |
| `co-change` | 漏改了耦合的另一处 | 添加同改规则，或从结构上消除 |
| `external` | 外部 CLI 行为与预期不符或发生变化 | 补录制场景 |
| `invariant` | 破坏了没有写下来的约束 | 写入模块「不变量」并锚定，能检查的改成检查 |
| `cross-platform` | 某一端漏改或行为不一致 | 补共享测试数据，或把逻辑下沉 |
| `logic` | 普通的实现错误，机制无关 | 无 |

CI 对缺少尾注或取值不对的 fix 提交给出警告（`pnpm aif commits <base>..<head>`，在 `.github/workflows/ci.yml` 的新提交检查里运行）。演进回路按模块汇总归因分布：某一类持续偏高，就说明对应的机制环节需要加强。这是本机制判断自身是否有效的主要依据。

### 5.7 规则的生命周期

每条同改规则、检查规则和知识条目都记录触发次数（`verify` 和 `aif context` 运行时在本地累计）：

- **升级**：同一条文档规则在归因里反复出现，就改为检查；检查反复被触发，就考虑从结构上消除；
- **退役**：180 天未触发的规则列入待删除项，由人确认后删除；
- **新增**：新增规则时说明来源（一次归因或一项耦合挖掘结果）。

根 `AGENTS.md` 只保留全仓库通用的规则，长度不再增加；模块相关的规则下沉到模块文档。

### 5.8 演进报告

`pnpm aif report` 汇总 §2 的指标、热点、变更耦合、CLI 漂移、待复核项与待删除项。输出写在本地数据目录，不进仓库，因为仓库公开、会话数据属于个人。由一个 Riffet 自动化任务每周运行一次并通知。报告用于两件事：决定改造优先级；对比改造前后同一模块的变化。

## 7. 分阶段

先用一个模块把三条回路完整跑通，验证有效后再推广，不先铺全仓库的基础设施。

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| 0 首个完整落地（2026-11-19 完成） | Codex 后端的模块文档与声明；`aif modules`、`aif context`、`verify`、`check:modules` 与行数基线；Codex App Server 的录制与回放（三个场景）；fix 尾注与 CI 警告；Codex 模块返工率基线 | `aif context` 输出在上限内；回放测试稳定且能发现行为变化；基线已记录（见下） |
| 1 服务端 | 服务端热点模块接入；Codex 的 rollout 与 hook 录制（从阶段 0 顺延，见下）；全部后端的场景矩阵（审批、中断、恢复、子 agent、压缩）；每周漂移检测；变更耦合挖掘；预热键派生；P0 Codex 后端拆分 | 服务端每个源文件都属于某个模块；Codex 后端所有输入通道都有录制、没有超限文件；30 天返工率低于基线 |
| 2 Web 与客户端逻辑 | Web 接入；同步测试数据扩展到 TypeScript；P0 Web 会话链改造；`aif report` 与每周自动化；工具调用记录目标路径，用于按模块归因和会话范围；锚点复核与规则触发计数 | 会话链没有超限文件；首次编辑前调用数低于基线；归因分布按周可见 |
| 3 推广 | Kotlin 与 Swift 接入；插件 SDK 的 agent 说明；引擎可用于插件仓库；会话内注入（可选）；P1、P2 模块 | 全仓库源文件都属于某个模块；超限文件基线持续下降；有规则按 §5.7 完成过升级或退役 |

阶段 0 记录的基线：Codex 模块近 30 天 81 个提交，fix 36 个（44%）；全仓库同期 659 个提交，fix 267 个（41%）。Codex 模块超限文件 3 个：`runtime.ts` 3934 行、`index.ts` 1515 行、`transcript-source.ts` 1068 行。首次编辑前调用数要等工具调用记录了路径才能按模块统计（阶段 2）。

阶段 0 顺延的两项：rollout 文件里有完整的系统指令和用户自己的全局指令，入库前要按解析器实际读取的记录类型做白名单，不能只做文本替换；hook 通道由 `observation.ts` 在启动 CLI 时挂载，录制需要同时运行它的 hook 服务。两项都放到阶段 1。

|---|---|---|
| 演进式架构的适应度函数（*Building Evolutionary Architectures*） | 架构约束写成可持续执行的检查；配合只减不增的基线 | — |

| VCR、Polly.js 的录制模式 | 回放与重录两种模式；录制数据的差异进代码评审 | — |

| ADR（架构决策记录） | 本机制的取舍记在 §10，推翻时追加新条目 | — |

## 9. 不做的事

- **不设综合评分和等级**。权重和分档只能靠主观校准，换一个代码库就要重来；agent 修改代码时需要的是具体的越界项。
- **演进回路不自动改规则和代码**。它只产出建议，由人确认后执行。
- **不整体重写 `docs/` 下的功能文档**。只补模块文档，并让功能文档链接过去。
- **不为覆盖率补测试**。回放测试只覆盖外部协议与跨端契约，与 `AGENTS.md` 的测试原则一致。
- **不引入新的构建或静态分析依赖**。导入关系沿用 `check:layers` 的实现；TypeScript 需要更精确的分析时，用仓库已有的 `typescript` 编译器 API。
- **会话数据不进仓库**。

## 10. 决定记录

| 日期 | 决定 | 原因 |
|---|---|---|
| 2026-11-19 | 不设综合评分，拦截只靠确定性检查，指标只看趋势 | 评分需要主观校准且会被优化成数字本身；agent 需要的是具体的越界项 |
| 2026-11-19 | 模块声明写在模块 `AGENTS.md` 头部，全局视图按需计算，不提交索引 | 集中维护的映射会与代码脱节；声明与说明放在一个文件里才能同步；扫描很快，提交的索引只会多一份要同步的文件 |
| 2026-11-19 | Codex 录制在 `CodexAppServerClient` 接口，不在 socket | 这一层正是回放要替换的位置；不需要在生产代码里加录制开关 |
| 2026-11-19 | 同改规则只警告，不拦截 | 改到触发点不一定要改另一处；能精确表达的规则应当从结构上消除 |
| 2026-11-19 | 层级只在 `LAYERS` 声明，模块文档不重复；生成物检查从生成脚本推导 | 同一事实写两处就会分叉；推导出的对应关系随脚本变化自动更新 |
| 2026-11-19 | 改动范围按会话确定 | 多个会话共享同一工作区，`git diff` 会混入其他会话的改动 |
| 2026-11-19 | 先在 Codex 后端完整落地，再推广 | 机制本身需要先验证有效，避免先铺基础设施再发现方向不对 |
