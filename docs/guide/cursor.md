# Cursor 原生会话与 CLI 配置

返回 [中文 README](../../README.zh-CN.md)。通用的会话行为见 [conversation.md](conversation.md)。

## 终端与结构化转录

Cursor 原生会话里跑的是**真正的 CLI**（tmux 持有），所以所有命令、子 Agent、选择器和对话框都与终端完全一致；同时服务端只读地跟随 CLI 自己的会话存储（`<config>/chats/<md5(cwd)>/<chatId>/store.db`），把它翻译成结构化的会话事件，于是**对话时间线**能显示消息、思考、工具行、diff、文件 chip、Todo 计划。

- **网页交互**：已识别的 AskQuestion 在对话页直接显示单选、多选、Other 和逐题操作；已知授权、信任与计划确认显示实际选项及上下文。提交前校验 CLI 当前画面，断线或结果不明时先同步，避免重复操作。未知、裁剪或无法准确执行的交互才展开终端。页头可随时切换「对话 / 终端」（桌面为标题右侧的切换图标，移动端在会话信息面板里）。
- **上下文用量**来自存储里的 `/context` 分解（系统提示词、工具定义、规则、Skills、MCP、子 Agent 定义、已压缩对话、对话），点环形进度可以看到分项。这是真实数据，不是估算。
- **历史消息在上下文压缩后仍可查看**：工作台按当前会话明确关联的压缩存档顺序恢复原始消息、回答和工具记录；连续多次压缩、旧摘要被移除后仍保留完整历史与消息身份。旧版网页已保存的发送记录按各次压缩前后的精确消息位置关联，图片附件不会因再次压缩而脱离原消息。较长历史继续按页加载；不会把其他分支或未关联的存储内容混进当前对话。存档尚未写完时等待重试，格式无法确认时保留当前记录并提示历史不完整。每次压缩在被压缩内容之后显示一条「上下文压缩」，展开可看摘要；压缩进行中状态会显示为正在压缩。
- **消息同步跟随 CLI 已提交的记录**：终端可能先显示流式文字和工具调用，CLI 将它们提交到会话存储后，对话视图会自动按顺序补齐。已绑定会话的消息读取与终端状态、进程扫描、子 Agent 和任务日志维护分开；这些检查变慢时，已经提交的主会话消息仍能继续同步。尚未提交或不属于当前会话分支的内容不会被拼进正式历史。
- **子 Agent**：`Task` 调用渲染成 `agent` 行，点击后**像打开会话一样打开该子 Agent 自己的转录**（按 agentId 跟随它自己的存储）。
- **模型切换不打开终端**：CLI 没有协议级的 set-model，`/model` 是 TUI 选择器、写它的私有配置又属于私有状态写入，所以工作台改用 `--model` **重启 CLI 并接着当前会话**。模型按家族分组（`claude-opus-5-thinking-high` 这类 id 里的维度被还原出来），思考程度（Effort）、Thinking、Fast 是独立开关，组合只从 CLI 自己列出的组合里取；如果当前选择是 CLI 的参数化形式（例如带 `context=300k`），切换时保留它、只改写它已经写明的维度。因为要重启，**正在进行的那一轮不能被打断**：这期间改的会被记下来，并在那一轮结束的那一刻自动重启生效；选择会记在会话上，「重新打开」也保持。
- **权限模式随时可选**：Allowlist（默认，逐次询问）、Auto-review（Cursor 的分类器自动放行安全调用）、Run Everything（`--force`，不再询问）——新建会话时在输入框下方选，会话内点输入框上方的同一个控件也能改（和换模型一样会重启 CLI 并接着当前会话；进行中改的会记下来，等那一轮结束再重启）。它就是 CLI 的启动参数，因此不写入 CLI 的私有配置。工作台会**从 CLI 自己的状态行读取当前生效的模式**：你在终端里用 `/run-everything`、`/auto-review` 改过之后，界面显示和后续重启都会沿用实际生效的那个。新建会话时**刻意不记住**上一次的选择——把「不再询问」变成所有新会话的默认是一种安全决定，不该被一次点击静默继承。切换模型重启 CLI 时，执行模式与权限模式都会重新带上，不会被悄悄重置回默认。
- **会话状态跟着 CLI 走**：终端进程活着不等于在干活。底部的状态行决定会话是「运行中 / 空闲 / 等待操作」，所以一轮结束后侧边栏不再一直转圈。没人看这个会话时，也会以几秒一次的频率只读地看一眼状态行。
- **一轮何时结束以 CLI 自己的记录为准**：状态行回到空闲、且会话存储里这一轮最后一条已提交的消息是不再调用工具的回答，两者都稳定约 3 秒后，这一轮记为完成；CLI 在后台任务结束后自己续写的回合同样按此结束。CLI 的 Stop hook 由模型服务端发起，部分网关从不发起它，所以它只用来补充失败或取消的结果，先到的一方生效。空闲了但存储里最后一步仍在等工具结果时，才显示「结果未确认」。
- **终端视图不再错位**：`capture-pane` 用裸 `\n` 分行（终端模拟器读作「下移一行、列不变」，pty 会替你补回车，WebSocket 不会），直接回放会让整屏斜着散开。服务端改为按行显式定位：滚屏历史用 `\r\n`，每个可见行写到第 1 列并清到行尾，最后把光标放回 CLI 自己的位置，TUI 的下一帧才不会画错地方。切换「对话 / 终端」或改变窗口大小都会重发这样一份快照。
- **读不到存储会明说**：CLI 的存储是私有格式，一旦解析不了，界面会显示「无法解析 Cursor 的会话存储（CLI 版本可能已更新）」，而不是给你一个空对话。`pnpm tsx scripts/probe-native-store.ts <项目目录>` 可以逐条检查这些假设是否仍然成立（只读、不落盘内容）。
- **同一工作区里的多个原生会话互不干扰**：会话存储按工作区分桶、不按终端分，光看修改时间无法判断新出现的对话属于哪个终端。所以工作台**直接问进程本身**——CLI 会把它正在使用的那份 chat 存储保持打开（SQLite WAL），于是每个终端都能精确认领自己的对话，`/clear`、`/resume`、`/fork` 也照样能跟上。只有既没有 `/proc` 也没有 `lsof` 的机器才退回「最新的 chat」，此时若同一工作区有两个原生会话，就保持各自绑定并说明原因，而不是把对方的对话读成自己的。
- **后台任务按 CLI 的异步标记识别**：只有显式 `block_until_ms: 0`，或执行结果返回 shell id、转入后台的原因、有效任务日志路径，才进入后台任务列表。普通同步 Shell 命令即使耗时较长，也只保留为对话里的工具记录。工作台把异步启动和 `AwaitShell` 等待合成**一个任务行**：标题、命令、运行中/完成/失败、耗时、退出码，展开就是输出。运行期间每秒只读地查看 CLI 自己的日志（`~/.cursor/projects/<项目>/terminals/<id>.txt`）；即使 Agent 从没 await 过它，也能跟踪状态和输出。等待本身和 schema 查询（`GetDynamicTools`）不再各占一行。
- **后台任务完成通知保留在发生的位置**：CLI 写入的任务通知会显示完成或失败状态、标题、完整命令及结果详情，并按精确 shell id 更新已有后台任务。CLI 为通知附带的内部提示不会显示成用户消息，也不会改变先前已结束回合的回答。Claude Code 的子 Agent 完成通知同理：CLI 把它作为 user 行写进转录，工作台解析成「子 Agent」通知行（名称、完成/失败、耗时、token、结果，可展开读结果，也可一键打开该子 Agent 的转录），而不是把整段 XML 当成人发的消息；那串通知本身仍然开启随后的回答所属的回合，否则那次回复会读起来像凭空出现。
- **子 Agent 以会话页打开，且区分「是否还在工作」**：`Task` / `Subagent` 调用渲染成一行，点击它（或标题栏「子 Agent」列表里的一项）会在对话区打开该子 Agent 自己的转录（按 `subagentInfo.toolCallId` 或调用结果的 agentId 跟随它自己的存储）。这一页与主会话用同一套转录视图：任务说明作为第一条消息，过程折叠、回答、跳转轮廓与「加载更早记录」都一样，只是没有输入框；顶部一栏显示状态、耗时并可返回主会话。子 Agent 里再派生的子 Agent 在此页继续打开，返回键逐级回退。后台启动的子 Agent（`run_in_background`）会立刻返回结果，所以「是否还在工作」以**它自己的存储在不在长**为准，而不是看那个已完成的结果行。DeepSeek Harness 的 `subagent` 调用同样展开为子 Agent 自己的转录：子 Agent 是独立的 DSH 会话，工作台从结果里的 `started subagent <id>` 找到它，按同一桥接接口只读跟随；「是否还在工作」看它最后一个回合有没有结束。Claude Code 的子 Agent 也走同一套页面：每个子 Agent 是 `subagents/agent-<agentId>.jsonl` 加一份 `agent-<agentId>.meta.json`，meta 里的 `toolUseId` 就是发起它的那次 `Agent`（早期版本叫 `Task`）调用，所以身份是确定的、不靠猜；嵌套子 Agent 的 `parentAgentId` 指向上一级子 Agent 的文件，在这一页里继续打开。Codex 的子 Agent 是同一台 app-server 上的独立 thread，spawn 那次 `collabAgentToolCall` 的 `receiverThreadIds` 就是新线程的 id，工作台按它 `thread/turns/list` 只读跟随（`sendInput`/`wait`/`followupTask` 只是对已有子 Agent 的操作，不会在列表里重复出现）；某个版本不再报 `receiverThreadIds` 时，这一行就退回普通工具行，而不是报错。
- **一轮结束时若工具仍停在运行中**（例如传输层报错导致 agent 没发终态），会显示「未完成」而不是永远转圈。

## 模型选择与命令

模型选择使用 CLI 的参数化模型协议：模型列表只列基础模型，思考程度、Fast、Max（大上下文）等作为独立选项，按当前模型实际提供的参数显示。会话内保存的选择形如 `claude-opus-5-5[effort=high,fast=true]`，发送前会重新应用，因为同一时刻 CLI 只有一份模型设置（切换模型同样要走 `--model` 重启）。与 TUI 一样，Cursor 会把最近的选择写入自身配置。

原生终端中的 `/summarize`、`/fork`、`/rewind` 等命令由 Cursor 自己执行。**工作台把 `/` 后面的内容原样交给 CLI**，所以 TUI 内置命令、自定义命令、Skills 全部可用（不在菜单里的也会照发）。

`/` 菜单按会话所在的项目和后端列出**内置命令与 Skills**（`GET /api/backends/:id/slash`，服务端缓存 60 秒，过期后先回旧清单、后台刷新）。清单各取自后端自己：Codex / TRAE CLI 用 app-server 的 `skills/list`，Claude Code 用 stream-json 的 `initialize` 控制请求（不调模型、关闭 hooks、不落会话），Droid 用 `droid.list_skills` / `droid.list_commands`，DeepSeek Harness 经 bridge 读它的 skill 注册表，Cursor 没有列举接口，按它自己的目录（`.cursor/skills`、`.agents/skills`、`.claude/skills`、`.codex/skills`，以及 `~/.cursor/skills-cursor`）扫描 `SKILL.md`。`/` 在消息开头或空白之后才打开菜单：**开头**列命令和 Skills，**句中**只列 Skills，而且只对能在句中调用 skill 的后端（Codex、TRAE、Claude Code、Droid、DSH；Cursor 只认开头）。选中后插入纯文本 `/name `，发出去的就是这段文字：Droid 与 DSH 自己识别句中的 `/name`；Codex 由服务端把文中命中清单的 `/name` 补成 `turn/start` 的 `skill` 输入项；Claude Code 只在开头展开 skill，所以一条只在句中点名**一个** skill 的消息会被改写为 `/name 原文` 再发给 CLI（同一次服务运行内转录显示原文，重启后读到的是 CLI 实际收到的改写；点名多个时原样发送，由模型自行判断）。以 skill 开头的消息按普通对话轮次跟踪，回复归入这条消息，不像内置命令那样在写入终端时就算完成。输入框下方会列出这条消息将调用的命令与 Skills，点 × 会从正文里删掉对应的 `/name`。

输入框对「菜单里没有的 `/xxx`」会多给一行「直接发送给 Cursor CLI」的提示：选中后按键原样发出。工作台不会声称它一定被当成命令执行——是否生效由 Agent 决定，结果以对话内容为准，不能因为发出去了就宣称执行成功。

## Cursor CLI 与自定义网关

新用户拉取仓库后，按上面的启动步骤安装依赖、构建并启动工作台。安装标准 Cursor CLI 后，在「设置 → Agent 与模型 → Cursor → 连接与默认模型」填写模型网关和 API Key，保存后执行 `riffet restart` 即可使用自定义网关。无需预先创建包装函数或个人 Key 文件；CLI 入口和配置目录可保持默认。直接使用 Cursor 默认服务时，可以沿用 CLI 已有的登录状态。

默认入口是标准 `cursor-agent`，通常无需手动指定。「设置 → Agent 与模型 → Cursor → 连接与默认模型」的常规连接设置只显示模型网关和 API Key；未单独设置 Agent 端点时，模型网关留空使用 Cursor 默认服务；Key 密码框留空会保留已保存的值。两端原本相同或均未设置时，修改模型网关会同步更新它们；已有的不同端点配置（包括 Agent 沿用 CLI 默认端点）会保留，并在页面上提示。

「高级设置」默认收起，提供自定义 CLI 入口、独立配置目录、单独的 Agent 端点和关闭自动更新选项。关闭“单独设置 Agent 端点”后，Agent 与模型网关地址同步；开启时可以指定其他端点，留空使用 CLI 默认端点。展开、收起或仅修改 Key 不会清空已保存的高级配置；保存只提交修改过的字段。自定义入口留空沿用服务启动时的入口，可填写可执行命令、绝对路径或 `shell:<函数名>`；配置目录用于隔离 CLI 配置和会话历史。

CLI 启动参数与 API Key 一起原子保存到服务端的私有 `cursor-cli.json`，文件权限为 `0600`；其他工作台设置继续使用 `settings.json`。API Key 不进入设置读取响应或诊断导出。使用显式 API Key 时，API Key 由工作台私有配置持久化，CLI 凭证存储使用进程内存；未提供 Key 时沿用 CLI 的登录方式。保存后执行 `riffet restart` 生效。当前进程继续使用启动时配置；原生会话、模型查询、配置浏览和管理命令共用同一份启动配置。已保存的 CLI 入口优先于启动命令提供的默认入口，避免旧服务记录继续选用此前的包装函数。

如果网关报 `expected h2 session, but ALPN protocol failed to negotiate`，它未能协商 CLI 默认使用的 HTTP/2。可在生效配置目录中的 `cli-config.json` 合并 `"network": { "useHttp1ForAgent": true }`，保留其他配置，然后重新打开相关 CLI 终端。默认配置目录是 `~/.cursor`；已有持久终端不会因仅重启网页服务而重新加载 CLI 配置。模型列表查询成功也不能证明 Agent 请求通路可用，应实际发送一条消息验证。

从已有包装函数迁移时，填入其实际使用的端点、API Key 和配置目录，就能直接用标准 CLI 获得相同效果。保留原配置目录可继续读取原来的 CLI 历史；更换配置目录或服务会切换历史范围，恢复旧会话时需要使用原目录和服务。

升级已有安装时，`daemon.json` 仍保留上次的 CLI 入口。尚未在设置页保存启动配置的安装，应先执行 `riffet stop`，再执行 `riffet start --cli cursor-agent`，然后在设置页填入原网关参数、Key 和配置目录并重启。需要继续使用 shell 包装函数时，将入口显式改为 `shell:<函数名>`。设置页可在 CLI 尚未就绪时打开。

也可以通过启动命令选择入口：

```bash
node dist/cli.js start --cli cursor-agent
node dist/cli.js start --cli /absolute/path/to/cursor-wrapper
node dist/cli.js start --cli shell:my_cursor
```

没有设置对应字段时，普通可执行入口继续继承服务进程的 `CURSOR_API_KEY`、`CURSOR_API_ENDPOINT` 和 `CURSOR_CONFIG_DIR`。未指定配置目录时使用 `~/.cursor`；`RIFFET_CONFIG_DIR` 仍可指定配置浏览目录。通用 shell 函数通过 `/bin/zsh -lic` 执行，参数作为位置参数传递，不拼接成 shell 源码。工作台不按函数名称猜测配置目录，也不重写 Cursor 的审批策略。
