# 服务器链接

日期：2026-11-19。状态：设计稿，未实现。

两台 Riffet 服务器（例如一台 Mac、一台 devbox）链接以后，打开其中任意一台的 Web，不切换服务器，就能看到两台的会话，并在任意一台上新建会话。Mac App、iPhone 和 Android 连接任意一台，也能看到全部。

本文给出全部可选的做法和取舍，并标明第一版做哪些。做哪些由项目自己选：有真实场景才做，不违背单节点原则（[architecture.md](guide/architecture.md) P6），并且算上长期维护的成本。

## 1. 目标与边界

**目标**

- 一个工作台：侧栏合并所有已链接服务器的会话；新建会话时先选在哪台服务器上运行。
- 对等：任意一台都能当入口，链接以后两个方向都可用（每个方向单独授权，见 §8）。
- 会话留在它所在的服务器上运行；入口服务器挂了，不影响另一台本机的使用。
- 对端的配置到对端自己的网页里改，本机不另做一套远程设置（§10「管理对端」）。
- 新功能按 [多服务器适配规范](guide/multi-server.md) 归类并适配。

**不做**

- 集群、共享数据库、选主、一致性协议。每台服务器仍是一个独立的单节点，链接只是两台之间的一条连接。
- 网络自动组网和 NAT 穿透（§9 推荐用现成方案）。
- 第一版不做把会话迁移到另一台服务器（§13 后续能力）。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 链接 | 两台服务器之间经配对建立的长期信任关系，加上承载它的隧道。界面上叫「互联」，链接上的另一台叫「互联的服务器」（[GLOSSARY.md](GLOSSARY.md)）。不叫「连接」：Mac 的「设置 › 连接」指 App 保存了哪些服务器，是客户端的事 |
| 入口服务器 | 客户端当前连着的那台。它合并列表、转发请求 |
| 所在服务器 | 会话、项目、终端实际所在的那台 |
| 对端 | 一条链接的另一端 |
| 发起方 / 接受方 | 隧道由哪一方建立。只取决于网络可达性，与授权无关 |

## 3. 模型

### 连接方向与授权方向分开

Mac 能连到 devbox，devbox 连不到 Mac，那么由 Mac 发起隧道。隧道建立后，两个方向的请求都走它：devbox 的 Web 可以在 Mac 上开会话，Mac 的 Web 也可以在 devbox 上开会话。每一台只决定「对端能不能操作我」，见 §8。

### 什么在哪里

| 留在所在服务器 | 由入口服务器负责 |
| --- | --- |
| 会话 journal、CLI、tmux、终端、附件 | 合并后的会话、终端、项目列表 |
| 项目、文件、Git、worktree | 合并搜索、⌘K |
| Agent 档案、模型源、模型目录、CLI 登录、扩展与插件 | 等待确认、完成等提醒和推送（§11） |
| 会话内的同步（[SYNC-V3.md](SYNC-V3.md)）、终端连接，经隧道直通 | 客户端的登录、Cookie、设备令牌 |

journal 必须和 CLI 在同一台机器上（P4）：转录文件、hook、MCP shim 都依赖本地文件系统。所以入口服务器不能把对端当作远程执行器，只能转发请求。

### 不成环

经链接到达的请求只返回所在服务器本机的数据：对端的列表不包含它从别处合并来的会话，经链接转来的请求也不能再转到下一台（§9 的中转除外，它只转发密文）。合并只在入口服务器做。

### 功能归属

每项功能先看它属于谁，分四类。写法细则和新功能的检查清单在 [多服务器适配规范](guide/multi-server.md)。

| 类 | 是什么 | 处理 |
| --- | --- | --- |
| A 工作对象 | 存在某台服务器上、用户工作时要找到的东西 | 合并显示并标出服务器，操作发到所在服务器。看得见的就要能搜到、能打开、能操作 |
| B 环境和配置 | 一台机器的能力和设置 | 不合并。只在用到时按目标服务器出现；要改就打开那台的网页（§10「管理对端」） |
| C 人的偏好与随手工具 | 属于用户本人、与机器无关 | 只用入口服务器本机的 |
| D 入口提供的服务 | 入口服务器对客户端提供的通道 | 用入口服务器本机的，可以作用在合并后的对象上 |

| 功能 | 类 | 结论 |
| --- | --- | --- |
| 会话、终端、项目 | A | 合并（§5） |
| 任务看板 | A | 合并；任务记 `dispatchedBy`，只有派活的助理跟进（见下「个人助理」） |
| 自动化 | A | 合并；创建时选服务器，在那台运行，入口离线也照常执行 |
| 高亮与收藏 | A | 存在会话所在的服务器，从哪台进来都看到同一份；目录收藏存的是路径，各台各管 |
| 分享 | A | 由所在服务器生成，用它的发布插件；它没有发布插件时不显示分享入口 |
| 侧边聊天 | A | 跟着所属会话 |
| @会话引用 | A | 第一版只能引用同一台上的会话；跨服务器要从对端取快照，后续再做 |
| 搜索、⌘K、助理的 `history_search` | A | 入口把查询并发发给各台，各台按自己的索引和可见范围检索，结果带 `serverId` 返回后合并。没按时返回或离线的，结果里写明不含它。入口不保留对端内容的副本 |
| 等待处理的计数与提醒 | A、D | 计数合并。第一版各台只给直接配对的设备推自己的会话，入口不代推；代推与去重在 L3（§11） |
| 插件、扩展、模型源、Agent 与 CLI 登录 | B | 设置里只有本机的；新会话选了对端时，Agent、模型、技能与工具的选项从对端读取 |
| 更新、诊断、`riffet doctor` | B | 「设置 › 互联」显示对端的版本、在线状态和是否需要更新；操作在对端的网页里做 |
| 个人助理 | C | 只显示本机的（见下） |
| 快速对话 | C | 只用本机的；对端的快速对话不进合并列表 |
| 外观、主题、主人资料 | C | 用本机的；打开对端的会话也按本机的主题显示 |
| 语音输入 | D | 用入口的转写，文字发往会话所在的服务器 |
| 飞书等 IM 通道 | D | 第一版只能把消息派到本机项目 |
| 设备（手机） | D | 第一版只供本机会话调用；对端会话调用入口的设备，后续再做 |
| 统计 | 待定 | §13 |

**插件分两层**。插件管理属于 B 类，不显示对端的插件。但插件依附在对象上做出来的东西，跟着对象所在的服务器走：

| 插件扩展的位置 | 例子 | 由谁提供 |
| --- | --- | --- |
| 对象 | 插件提供的 Agent（Cursor 就是一个插件）、`session-view`、`taskProviders`、`runtimeControl`、视图里执行的命令 | 对象所在的服务器。打开 devbox 上的 Cursor 会话，由 devbox 的 Cursor 插件解析和渲染，视图包经链接取来 |
| 全局 | `sidebar` 视图、插件页、设置页里的操作、`avatarStyles`、`imChannels` | 只用本机的。本机插件里与项目相关的视图也不出现在对端的项目上，因为本机插件读不到那台的项目 |

所以 Mac 上没装 Cursor 插件，也能打开 devbox 上的 Cursor 会话；但新会话页选 Mac 时，没有 Cursor 可选。

### 个人助理

每台服务器有自己的助理（[ASSISTANT.md](ASSISTANT.md)），打开哪台的 Web，看到的就是哪台的助理。不合并，不经链接打开对端的助理。

- **互不可见**：合并列表排除对端助理项目里的会话；`session_list`、`history_search` 也查不到对端助理的对话。
- **知道自己连着谁**：新增只读能力 `workbench.servers`，列出互联的服务器、在线状态和两个方向的开关；每轮告诉模型的内容（ASSISTANT.md §5.1）带上一份精简的服务器列表。
- **能去哪里**：只能去本机有权操作的对端（`outbound`），不超过链接允许的范围。查询类工具（`list_projects`、`session_list`、`task_list`、`history_search`、`server_status`）的结果带服务器，可以按服务器筛选；工具在数据所在的服务器执行，可见范围和截断规则由那台判断。
- **派活**：`task_create` 可以指定对端的项目。任务存在对端的看板里，开始后由对端用自己的 Agent、模型和登录状态开会话；执行会话的 `task_submit`、`task_ask` 由对端本机注入。计划卡片标出服务器。同一个仓库在两台上都有时，先看记忆里的偏好，没有就问。
- **跟进归派活的助理**：任务记 `dispatchedBy: {serverId}`。只有派活的助理跟进，对端的助理在看板上看得到这个任务，但不去跟进，它的计划卡片也只列自己派的任务。触发跟进的会话状态和任务事件经链接推给派活方；`task_continue`、`task_rework` 经链接发给对端的会话；委托可以订阅对端的任务。
- **离线**：目标服务器离线时派活直接失败，助理如实告知，不替用户在别处排队。派活方离线（例如 Mac 睡眠）时，对端的任务照常运行，跟进在派活方恢复后按 ASSISTANT.md §7.2 的补看规则补上。想让夜里有人一直盯着，就在一直在线的那台上交代。
- **权限**：沿用 ASSISTANT.md §6 的三级。启动改代码的任务先出计划卡片，`dispatch = 'all'` 同样约束跨服务器的任务。设置类工具（`setting_set`、`agent_defaults_set`）只作用于本机。对端的操作记录标明「<服务器名> 的个人助理」。
- **记忆分开**：两个助理各学各的。以后如果有需要，可以经链接同步 `USER.md`，记忆本身仍各管各的。

## 4. 寻址与转发

### 标识

- 服务器：`serverId`（`apps/server/src/server-id.ts`，持久保存的 UUID，重启不变）。
- 会话、项目、终端的 id 都是 UUID，跨服务器不冲突，合并时不需要改写 id，只给列表数据加上 `serverId`。
- 客户端按 `(serverId, id)` 存放；会话的路由和深链带上 `serverId`。路由表里只有 id 时，按合并列表查出所在服务器。

### 服务器列表

`GET /api/servers` → `{servers: ServerInfo[]}`，第一项是本机：

```ts
interface ServerInfo {
  id: string;                 // serverId
  name: string;               // 对端自报，本机可改显示名
  self?: true;
  online: boolean;
  version?: string; protocol?: ProtocolInfo;
  compatible: boolean;        // 协议版本落在本机接受的范围内
  inbound: boolean;           // 对端可以操作本机（本机决定）
  outbound: boolean;          // 本机可以操作对端（对端决定，握手时告知）
  lastConnectedAt?: string;
}
```

`bootstrap` 带上同一份列表，供首屏直接渲染。

### 转发

- `/api/servers/<serverId>/<path>` 由入口服务器经隧道原样转给那台的 `/api/<path>`，包括 HTTP、SSE、WebSocket 和上传。`<serverId>` 是本机时，等价于 `/api/<path>`，所以客户端可以统一使用带服务器的路径。
- 对端用现有的路由处理，不另写一套远程接口。
- 入口服务器在转发的请求上加 `x-riffet-link-origin: <设备 id>`，标明是从入口服务器的哪台客户端发起的，供对端审计（§8）。客户端自己带来的同名头先删掉。
- 转发的请求不经浏览器，所以对端不做 CSRF、`Origin` 和 `Host` 校验，身份靠隧道的 TLS（§6）。
- 入口转发时带上发起请求的客户端的 `x-riffet-features`。对端按它隐藏客户端解不了的会话和项目（`registerProjectVisibilityHook`、`registerSessionVisibilityHook`），和客户端直连时一样。
- 入口服务器**不**在自己的源下提供对端的 Web。对端的页面代码一旦运行在入口的源下，就能带着入口的 Cookie 和 CSRF 令牌调用入口的接口，绕过每个方向的授权。打开对端网页的做法见 §10「管理对端」。

### 对端身份

经链接到达的请求，在对端的身份是 `link:<serverId>`。本机没有允许对端入站（`inbound: false`）时，这条链接上来的请求一律拒绝，包括只读的列表，对端看不到本机的任何东西。允许入站时，权限等同本机用户，但不能削弱本机对自己的控制权，以下接口一律拒绝（403 `LINK_FORBIDDEN`）：

- 链接管理：增、删、改方向，生成邀请；
- 配对、访问令牌、设备令牌与设备撤销；
- `/api/servers/*`（不再转发，见 §3）。

密钥原文（APNs 密钥、模型源密钥）现有接口本来就不返回，经链接也一样。更新和重启不在禁止之列：对端的配置要到对端的网页里改（§10），版本不兼容时也靠这条路更新。

每条路由都要声明经链接来的请求怎么处理（照常处理、只回答本机部分、拒绝），登记在一张按路由模式的策略表里；没有登记的默认拒绝，见 [多服务器适配规范](guide/multi-server.md) §3.1。

经链接新建的会话记下来源（`Session.origin` 增加 `{kind: 'link', serverId}`），会话列表据此标出从对端开的会话。这一条随 L2 的合并列表一起做。

经链接来的请求一律算远程请求（入口给它加 `x-riffet-link`，`auth.ts` 的 `proxiedRequest` 据此判定），所以项目外文件读取默认关闭，与 [SECURITY.md](SECURITY.md) 信任边界第 7 条一致。L1 实测：在对端浏览目录、登记新项目（`/api/browse`、`/api/projects`）不受这条影响，照常可用（`links/links.test.ts`）。

### 版本

握手时交换 `ProtocolInfo`，新增协议特性 `server-links-v1`。对端版本不在本机接受的范围内时，`compatible: false`：列表里照常显示，但不能打开它的会话和新建会话，提示打开那一台的网页更新。

## 5. 列表合并

- 入口服务器经隧道订阅每个对端的 `/api/lists/stream`，按 [LIST-SYNC.md](LIST-SYNC.md) 增量读取，再合成一条列表流给自己的客户端。
- 修订从一个数改成每台服务器一个：`changed.data.servers: {[serverId]: {revision, terminals, projects, …}}`。`SessionListDelta` 加 `serverId`，`removed` 也按服务器区分。旧字段继续只描述本机，没有声明 `server-links-v1` 的客户端只看到本机，行为不变。
- 契约只做可加改动（`pnpm gen:contracts --check` 要求）：`serverId` 在线上是可选字段，客户端合并后的类型里才是必填。列表流的 `changed` 事件和 bootstrap 现在没有命名类型，先在 `packages/contracts` 里补上。
- 会话内的同步流和终端不合并，客户端经 `/api/servers/<id>/…` 直连所在服务器。
- **对端离线**：入口服务器在内存里保留它最后一份列表（随链接删除而释放），侧栏照常显示并标为离线。打开会话只显示客户端本地缓存，不能发送。重连后各流从游标续传。
- 上限（每台对端保留的列表条数、合并后推送的去抖）进 `packages/contracts/src/budgets.ts`。

## 6. 隧道

### 分层

```
连接方式（direct：WebSocket；ssh：标准输入输出；插件提供的其他方式）
  └─ TLS 1.3：双方用自签名的 Ed25519 证书，按配对时记下的指纹核对
       └─ HTTP/2：多路复用、流控
            └─ 每个转发的连接一条 CONNECT 字节流，里面是原样的 HTTP/1.1（包括 SSE、WebSocket 升级、上传）
```

- **TLS 是链接自己的，不依赖传输层**：底下走明文 HTTP、HTTPS 还是反向代理都一样安全。用 Node 自带的 `tls`：发起方 `tls.connect({socket})`，接受方 `new tls.TLSSocket(duplex, {isServer: true})`，双方都提交证书，用指纹而不是 CA 校验。不引入新的加密库。
- **两个方向各用一个 HTTP/2 会话**：HTTP/2 只能由客户端发请求，所以发起方建立两条隧道，一条自己当 HTTP/2 客户端，另一条自己当 HTTP/2 服务端，对端当客户端。HTTP/2 的角色与谁先发起连接无关。
- **请求进入对端后**：对端把这条 CONNECT 流当作一个连接交给自己现有的 HTTP 服务器（`server.emit('connection', stream)`），并在这个连接上标记它来自哪条链接。路由、中间件、WebSocket 升级都与普通请求相同，只是身份换成 `link:<serverId>`。标记在连接对象上，不在请求头里，所以经隧道发来的内容伪造不了它。不用 RFC 8441 extended CONNECT：普通 CONNECT 已经能承载 WebSocket 升级，对端也不需要为 WebSocket 单独处理。
- **证书**：Node 能解析证书但不能生成，`links/identity.ts` 自己按 DER 编码一张最简的自签名证书，签名用 Node 的 Ed25519，不引入依赖。

### 实测（L0，2026-11-21）

`node --import tsx scripts/probe-link-tunnel.ts`，Node 24.19，Apple Silicon，进程内回环。11 项检查全部通过：指纹不符被拒绝；TLS 1.3；JSON、SSE、WebSocket 升级、20 MB 上传、32 MB 下载、20 个并发请求经隧道到达对端的普通 Fastify 路由，并带着链接标记；反方向（接受方向发起方发请求）；隧道断开后新请求立即失败。

| 指标 | 隧道 | 直连回环 |
| --- | --- | --- |
| WebSocket 往返 p50 / p95 | 0.27 / 0.56 ms | 0.06 / 0.10 ms |
| 32 MB 下载 | 184 ms | 29 ms |
| 小请求 p50（每次新开 CONNECT 流和 HTTP/1.1 请求） | 4.2 ms | — |

实现时要照做的三点：

- **层与层之间隔一层内存管道**：Node 的 HTTP/2 直接放在「底层是 JS 流的 TLSSocket」上时，会接管 TLS 句柄、读到 TLS 下面的原始字节；HTTP 服务器拿到 Http2Stream 时也会接管它的原生句柄、写出错乱的数据。两处都交给 `stream.duplexPair()` 的一端，真实的流接到另一端，代价是多一次拷贝。
- **底层流关闭时显式销毁 TLSSocket**：底层是 JS 流时，TLSSocket 收不到关闭，握手会一直挂着；握手另设时限。
- **调大 HTTP/2 的会话内存**：默认 10 MB 的 `maxSessionMemory` 会在大文件上传中途重置流。取值进 `LINK_BUDGET`。

### 连接方式是扩展点

```ts
interface LinkTransport {
  id: string;                                       // 'direct' | 'ssh' | 插件声明的 id
  dial(target: LinkTarget, signal: AbortSignal): Promise<Duplex>;
}
```

- `direct`：发起方连接对端的 `GET /api/links/tunnel`（WebSocket 升级），取得流。
- `ssh`：发起方运行 `ssh <host> riffet link stdio`；远端的这个命令经本机回环连接自己的服务器并转发标准输入输出。对端可以只监听 `127.0.0.1`，不开 `--auth`，也不暴露端口。
- 插件可以提供其他方式（例如公司内网的专用通道），接受方仍是同一个入口。核心只负责身份、加密、授权和路由。

### 生命周期

- 发起方断线后按指数退避重连（上限进 `budgets.ts`）；Mac 睡眠唤醒、换网络时立即重试一次。
- 隧道里每 15 秒心跳一次，连续 3 次没有回应就断开重连。
- 断开时进行中的请求全部中止；客户端的同步、列表、终端按各自现有的方式重连续传。
- 每条链接的同时打开的流数、单个请求体、请求速率都设上限，进 `budgets.ts`，超出时拒绝，不影响本机自己的使用。

### 存储

- `<stateDir>/link-key.pem`、`link-cert.pem`：本机的长期密钥与自签名证书，0600。Mac App 托管服务时可以放进 Keychain。
- `<stateDir>/links.json`，0600：`{serverId, name, transport, target, peerFingerprint, inbound, createdAt, lastConnectedAt}[]`。
- 换密钥：用旧链接发一条由旧密钥签名的轮换消息，对端更新指纹，不用重新配对。

## 7. 配对

原则：不新建信任，借用用户已经在用的通道。走哪条路，链接配对时的安全性就和那条通道一样。

### 链接串

```
riffet-link:v1:<base64url({url, serverId, name, fingerprint, inviteId, key, expiresAt})>
```

- 由一方生成，5 分钟内有效，只能用一次。
- `fingerprint` 让加入方第一次连接就能核对对端，不需要「首次信任」。
- `key` 只在本地用来计算 HMAC，从来不在网络上发送：加入方连上以后提交 `HMAC(key, inviteId ‖ 双方指纹)` 和自己的证书指纹，生成方核对后记下它的指纹，邀请作废。
- 不用现有的 6 位配对码，是因为它太短：中间人拿到一次 HMAC，离线几毫秒就能把码试出来。

### 四个入口

| 入口 | 做法 | 安全性等于 | 期 |
| --- | --- | --- | --- |
| SSH | Mac 上 `riffet link ssh devbox`：经 SSH 在 devbox 上运行 `riffet link invite --json` 取邀请，然后加入，之后的隧道也走 SSH | SSH 密钥 | L1 |
| 链接串 | 一方运行 `riffet link invite`，或在「设置 › 互联」生成；另一方运行 `riffet link join <串>`，或粘贴到 Web | 复制粘贴本身 | L1 |
| 浏览器授权 | 在 Mac 本机的 Web 里点「连接服务器」，填 devbox 的地址 → 跳到 devbox 的 Web（已登录），确认请求方和方向 → 跳回 Mac，完成 | 浏览器到 devbox 的那条连接 | L3 |
| Mac App | devbox 已在 Mac App「设置 › 连接」的服务器列表里时，那一行打开「与本机互联」。App 用已有的 devbox 设备令牌取邀请，交给本机服务器加入 | App 到 devbox 的那条连接 | L3 |

浏览器授权的细节：

- Mac 服务器生成 `state` 和自己的指纹，浏览器跳到 `<devbox>/link/authorize?name=…&fingerprint=…&state=…&return=…`。
- `return` 只允许回环地址，防止被人构造链接把邀请骗到别处；Mac 的 Web 不在回环上时，改用链接串。
- 授权页和 Mac 的页面都显示一个由双方指纹算出的 6 位比对码，用户确认两边一致后才允许，防止有人诱导你批准他的机器。
- 从 devbox 的 Web 发起时，devbox 连不到 Mac，就生成一个指向 `http://127.0.0.1:4337/link#invite=<串>` 的链接。浏览器就在 Mac 上，点开就进了 Mac 本机的 Web。邀请放在 URL 的 `#` 后面，不进请求日志和 Referer。

SSH 的注意点：

- 远端非交互 shell 的 PATH 里可能没有 `riffet`，允许用 `--remote-command` 指定路径。
- 断线重连要求 SSH 能免交互登录，并且 LaunchAgent 能用到 ssh-agent。证书每天过期的环境里，过期后链接会离线，界面提示重新认证。

### 方向在配对时确认

每一台只决定自己的入站方向（「允许对端在本机开会话」），在配对流程里逐项勾选，勾选项旁边写明代价（§8）。之后在两边的「设置 › 互联」里都可以单独修改或断开。

## 8. 安全

| 威胁 | 措施 |
| --- | --- |
| 网络窃听和冒充 | 隧道内 TLS 1.3，双方按配对时记下的指纹验证证书；隧道里不传 bearer 令牌 |
| 配对被劫持 | 链接串的密钥不上网，指纹在链接串里固定；浏览器授权限制 `return` 只能是回环地址，并要求比对码一致 |
| 中转节点偷看或篡改 | 中转只转发密文；接受方只认直接配对过的机器，中转方不能替别人担保 |
| 对端试图削弱本机的控制权 | 链接管理、配对、令牌与设备撤销对 `link:*` 一律拒绝；没有声明链接处理方式的路由默认拒绝（§4） |
| 想撤销时撤不掉 | 任意一方都能单方面断开：隧道立即关闭，指纹作废，进行中的请求中止，入口缓存的对端列表清除。Mac 菜单栏有「断开所有互联」 |
| 不知道对端做了什么 | 对端发起的新建会话、打开终端、答复审批、写文件，记在本机「设置 › 互联 › 那台服务器」下（附发起它的客户端，条数有上限）；会话列表标出从对端开的会话 |
| 资源耗尽 | 每条链接的流数、请求大小、请求速率设上限（§6） |
| Agent 被提示注入后借链接操作对端 | 普通会话的 Agent 用不到链接，Riffet MCP 不给它们链接工具。唯一的例外是个人助理（§3「个人助理」），沿用它的三级权限，派改代码的任务先出计划卡片 |

**保证不了的**

允许 devbox 操作 Mac，那么 devbox 被拿到 root，就等于 Mac 也被拿到了你的用户权限。devbox 必须持有链接私钥才能用这条链接，Agent 本身又能执行命令，限制目录起不到隔离作用。同理，配对过 devbox 的所有客户端，也都间接拿到了 Mac 上的权限。

所以每个方向要单独判断值不值得信任：

| 想要的 | 要开的方向 | 代价 |
| --- | --- | --- |
| 在 devbox 的 Web 上开 Mac 会话 | Mac 允许 devbox | devbox 被攻破，Mac 也会被攻破 |
| 只在 Mac 的 Web 上统一使用两台 | devbox 允许 Mac | Mac 被攻破，devbox 也会被攻破；devbox 碰不到 Mac |

devbox 是多人共用的机器时，建议只开「devbox 允许 Mac」。

浏览器到入口服务器这一段没有 TLS，这是现有缺口（[SECURITY.md](SECURITY.md) 已知缺口第 1 条），链接管不到。这一段继续用 Tailscale、SSH 隧道或 HTTPS 反向代理。

## 9. 连不通时

| 情况 | 做法 | 状态 |
| --- | --- | --- |
| 一方能直接访问另一方的端口 | `direct` | L1 |
| 端口不通，但能 SSH | `ssh` | L1 |
| 只有反方向能连 | 由能连的一方发起，其余相同 | L1 |
| 都进不来，但都能往外连 | Tailscale 这类覆盖网络：加入同一个 tailnet 后就回到直接可连，Riffet 不用改 | 文档推荐 |
| 同上 | 第三台 Riffet 服务器中转（比如一台公网 VPS）：两边都连它，它只转发端到端的密文 | 有第三台机器的需求时再做 |
| 同上 | 轻量中转服务（`riffet relay`），只转发密文、不存数据 | 有人不想跑完整的 Riffet 时再做，可以做成插件 |
| 同上 | 自己做 NAT 穿透 | 不做：现成方案已经做得很好，自己做成本高 |
| 同上 | 由 Riffet 项目运营公共中转 | 不做：违背 P6，还要长期承担运维和信任成本 |
| 两边之间完全没有网络路径 | — | 连不上 |

devbox 在公司内网时，从内网往外连到个人 VPS 或中转服务，可能违反公司的网络规定。这种情况优先用公司 VPN。

## 10. 界面

按设计规范做，文案只写用户推断不出的信息。界面细节在实现前对照 [设计体系](design/system/README.md) 再定稿。

- **侧栏**：项目本来就属于某一台服务器，在项目分组上标出服务器名，只有一台时不显示。按时间排的视图里，会话行带服务器名。不另加一层「服务器」分组。
- **新会话页**：在选项目之前加选服务器，默认是上次用的那台；项目、Agent、模型都从选中的服务器读取。
- **离线**：离线服务器的会话照常列出，标为离线，不能新建会话也不能发送。
- **设置 › 互联**（新分区）：列出互联的服务器，每台显示在线状态、版本、本机的入站开关、操作记录、「打开 <名字> 的网页」和断开；添加互联时生成或粘贴链接串。新增的文案只有入站开关和它旁边的代价说明，例如「允许 devbox 操作这台电脑」，以及「devbox 被他人控制时，对方也能操作这台电脑」。
- **管理对端**：设置只管本机，设置页现有的分组不动，也不加服务器选择。要改对端的插件、模型源、Agent，或者更新对端，就打开对端自己的网页，在那里改，本机不再做一套远程设置。「打开 <名字> 的网页」在新标签页打开对端自己的地址（对端自报的地址，或者链接时用的地址），在那里登录。经链接取一次性码免登录的做法暂不做：那等于把对端整个网页会话交给链接身份（§12 现状）。浏览器访问不到对端时（例如在 devbox 的 Web 上，而 Mac 在 NAT 后面），只显示对端的地址。入口在独立端口上代理对端网页的做法留到确有需要时，前提是不同源、单独鉴权（§4）。对端的链接管理、配对和令牌经链接不能调用，要改只能直接登录那一台。

## 11. 各端

- **Web**：`lib/api.ts` 的约 270 个调用改成先按服务器绑定（`api.for(serverId)`）；请求层之外直接写路径的约 40 处（`lib/tasks.ts`、`plugins/*`、`sync/protocol.ts` 等）和 4 处 `new WebSocket` 迁进请求层。`listsStore` 和按 id 存放的各 store（选中项、标签页、任务、高亮、目录、会话状态）带上 `serverId`。插件视图本来就在不透明源的 iframe 里运行，对端的视图包可以直接渲染；宿主桥接调用要路由到对象所在的服务器。
- **Mac App、iPhone、Android**：`RiffetApi` 一个实例绑定一个 `baseUrl`，请求都经几个集中的方法发出，所以每台对端建一个带 `/api/servers/<id>` 前缀的实例即可，不改各处路径。要改的是 `SessionStore`、`ListsFeed` 和各缓存按 `serverId` 存放。按 [Mac 客户端范围规范](guide/mac-scope.md)：合并侧栏和新会话选服务器属于 W，随功能跟进；互联的管理是服务器上的配置，属于 M，Mac 只给一个打开 Web 的入口；菜单栏「断开所有互联」和 §7 的一键互联要用菜单栏和 Keychain 里的设备令牌，属于 S。
- **推送**：第一版各台照旧只给直接配对的设备推自己的会话，入口不代推，也不会重复提醒。L3 再由入口代推对端会话的提醒：喂入合并列表、载荷带所在服务器以便转发通知上的操作、按 `(所在 serverId, sessionId, kind)` 去重。

## 12. 分期

| 期 | 内容 |
| --- | --- |
| L0 探针 | Node 24 上：TLS 跑在 WebSocket 之上、HTTP/2 跑在这层 TLS 之上、经 extended CONNECT 承载 WebSocket；终端和同步流经隧道的延迟与吞吐；`ssh` 标准输入输出传输；LaunchAgent 能否用到 ssh-agent |
| L1 链接 | 密钥与 `links.json`；邀请与加入接口；`direct` 和 `ssh` 两种连接方式；双向隧道；`/api/servers` 与转发；`link:*` 身份、入站开关和禁止的接口；路由策略表及其覆盖检查；操作记录；`riffet link` 命令；「设置 › 互联」 |
| L2 合并 | 契约加 `serverId` 和 A 类对象清单；`Session.origin` 的 `link` 来源；按服务器分开的修订与合并列表流；bootstrap 带服务器列表；Web 请求层与各 store，`check:servers` 上线；新会话页选服务器；侧栏服务器名；离线；合并搜索与 ⌘K（A 类看得见就要能搜到，所以和合并同期）；核心登记各扩展点的作用范围，对象类扩展跟着对象走 |
| L3 统一入口 | 浏览器授权与 Mac App 一键互联；是否经链接取对端网页的一次性码；入口代推对端会话的提醒与去重 |
| L4 其他客户端 | Mac App、iPhone、Android 接入合并列表 |
| A1 助理：查询与派活 | `workbench.servers` 与每轮的服务器列表；查询类工具跨服务器；在对端建任务、开任务；`dispatchedBy`；计划卡片标服务器；排除对端助理的会话。前置 L2 |
| A2 助理：跟进 | 对端经链接推送任务事件；派活方跨服务器跟进，`task_continue`、`task_rework`；委托订阅对端的任务。前置 A1 |
| A3 按需 | 在对端建项目（先问用户）；同步 `USER.md`；设备跨服务器使用 |

**现状（2026-11-21）**：L0、L1 已实现，「打开对端网页的一次性码」除外：现在「打开对端的网页」直接打开对端地址，要在那里登录。一次性码等于把对端的整个网页会话交给链接身份，其中包括它的互联与设备管理，和 §8「经链接不能削弱对端对自己的控制权」冲突，留到 L3 和浏览器授权一起定。核心测试在 `apps/server/src/links/links.test.ts`。

一条已知限制：拨号的一方在对端离线时断开，对端收不到通知，那边的链接一直显示离线，要在那边手动断开；对端是拨号方时，它下次拨进来会得知链接已断开。

每期都按 [AI 友好工程机制](guide/aif.md) 补模块文档和验证，并按 [多服务器适配规范](guide/multi-server.md) 落地它在这一期要求的检查。隧道、链接身份、路由声明与禁止接口属于「鉴权与数据隔离」，需要核心测试。

## 13. 待定与后续

**待定**

- L3 推送去重：手机同时配对了所在服务器和入口服务器时，由谁发提醒。倾向由入口服务器跳过那些也直接配对了所在服务器的设备，需要设备在两台上能被识别为同一台。
- 版本不兼容时，是只禁止新建会话，还是连已有会话也不能打开。更新本身在对端的网页里做（[UPDATE.md](UPDATE.md)）。
- 统计：倾向合并显示、可以按服务器筛选；也可以只看本机。优先级低。

**后续能力**（目标达成之后，各自按需立项）

- 把会话交给另一台服务器接着跑（复用 `orchestration/handoff-summary.ts` 的交接摘要）。
- 设备跨服务器使用：手机只配对 devbox，Mac 上的会话也能调用它。
- @会话引用跨服务器。
- 飞书等 IM 通道把消息派到对端的项目。
- 第三台服务器中转与轻量中转服务（§9）。
