# Riffet 任务看板与助理

日期：2026-11-16（初稿 2026-11-13）。状态：P1、P2 的服务端与 Web 已实现（Mac 未开始）；P4 助理主对话的服务端与 Web 已实现，助理本身的设计移到 [ASSISTANT.md](ASSISTANT.md)；P3 跟进的服务端与 Web 已实现（[ASSISTANT.md](ASSISTANT.md) §7.2）。交互原型：[design/task-board-demo.html](design/task-board-demo.html)。

## 1. 问题与目标

**问题。** 用户同时推进很多件事。Agent 每做完一轮就停下，用户得自己在会话之间找，判断它做完没有、下一步该做什么。

本机最近 14 天的记录（2026-11-01 至 11-14，不含快速对话）：

- 319 个会话分布在 15 个项目里，平均每天动 20 多个。
- 有 Agent 在跑的时间里，43% 同时跑着两个以上。
- 用户连续发出的两条消息，72% 不在同一个会话。
- 一轮结束后，用户回到这个会话的间隔：中位数 5 分钟，四分之一超过 19 分钟，十分之一超过 1.5 小时。

**目标。** 少打扰用户，少让 Agent 等用户。用两个数衡量，显示在统计页：

| 指标 | 算法 |
| --- | --- |
| 每天打扰次数 | 一天里送到用户面前、需要用户处理的条目数：审批、提问、待验收、推不动的事 |
| Agent 等用户的时长 | 会话停下等用户处理的总时长，从停下算到用户处理为止 |

每一项设计都要说明它降低了哪个数。降不了的不做。

记录方式：会话进入「等你确认」或一轮结束停下时，服务端在 `attention_log` 记一笔开始时间，会话再动起来、或它所属的任务被标为完成时，补上结束时间（`apps/server/src/work-items/attention.ts`）。提问和待验收从任务活动里数。还没结束的等待不计入；会话没人回来就归档了，这一笔删掉。开始记录之前的日子显示为未知，不算作 0。

## 2. 概念

只有三个新概念。会话保持现状，不改名，不改界面。

| 概念 | 是什么 |
| --- | --- |
| 任务 | 一件要做成的事。下面挂着做它的会话，有自己的状态和验收标准。代码名 `WorkItem` |
| 助理 | 用户的常驻 Agent（[ASSISTANT.md](ASSISTANT.md)）。与看板有关的是两部分：**主对话**，用户在这里说要做什么，它派出任务；**跟进**，在后台盯着进行中的任务，不占主对话 |
| 收件箱 | 唯一会打扰用户的地方。只放要用户决定的事 |

## 3. 流程

```
┌──────┐              ┌────────┐               ┌────────┐
│  你  │ ──说要什么─▶ │  助理  │ ──派任务──▶  │  会话  │
└──────┘              └────────┘               └────────┘
    ▲                                               │
    │                                               │ 停下
    │                                               ▼
┌──────────┐                               ┌────────────────┐
│  收件箱  │ ◀───────只在要你决定时─────── │  跟进（后台）  │
└──────────┘                               └────────────────┘
```

任务也可以由用户自己建：在看板上新建，或者把已有会话转为任务。之后的流程相同。

会话停下时，跟进按下表处理：

| 会话停下的情况 | 跟进做什么 |
| --- | --- |
| 执行者交付了 | 对照验收标准核对证据（§6）。通过，进收件箱等用户验收；不通过，把具体问题作为返工意见发回会话 |
| 在等审批，或在问用户 | 直接进收件箱。审批只由用户回答 |
| 出错，或停在中间、没有说明 | 读这个会话：能推就推（让它继续、回答它自己能答的问题、到点再看）；推不动才进收件箱 |

跟进判断的依据：

1. 会话自己的状态：在跑、等审批或提问、出错。
2. 执行者的汇报：交付或提问（§6）。
3. 前两者都没有时，跟进才读这个会话的内容。

两条规则保证跟进不碍事：

- **用户在场时不插手。** 用户 10 分钟内在某个会话里发过消息，跟进就不处理这个会话。用户离开后会话停下了，才轮到跟进。
- **不改代码，不转述。** 跟进发给会话的只有三种消息：「继续」、对问题的回答、返工意见。用户随时可以直接进会话说话。

推不动的界限：同一个任务连续推了两次还没有进展，或者返工两轮仍不通过，就进收件箱，附上跟进的判断。

## 4. 任务

### 4.1 状态

```
 看板上新建                         看板上新建并开始，或转为任务     
     │                                           │
     ▼                                           ▼
┌────────┐                        ┌──────────────────────────────┐
│  待办  │ ──── 开始（你）─────▶  │            进行中            │
└────────┘                        │                              │
                                  │  运行中                      │
                                  │  等你：审批、提问            │
                                  │  失败                        │
                                  │  空闲：回合结束、没交付      │
                                  └──────────────────────────────┘
                                      │ ▲
                       交付（执行者） │ │ 返工（你或跟进）
                                      ▼ │
                                  ┌──────────────────────────────┐
                                  │            待验收            │
                                  └──────────────────────────────┘
                                      │
                       验收（只有你） │
                                      ▼
                                  ┌──────────────────────────────┐
                                  │             完成             │
                                  └──────────────────────────────┘
```

- 方框是存储的状态。「进行中」框里的四行是实时标记，从会话状态推导，不存储，规则在 `packages/contracts/src/session-attention.ts`。
- 跟进上线后，交付先经跟进核对，通过了才进待验收。
- 用户可以把卡片拖到任何一列；没结束的任务可以取消；完成或取消后再开会话，任务回到进行中。
- **只有用户能改成完成。**

### 4.2 字段

| 字段 | 说明 |
| --- | --- |
| `number` | 服务器内递增，显示为 `#128`。任务可以跨项目，所以不按项目分号 |
| `title`、`description` | 描述是 Markdown |
| `criteria` | 验收标准，一条一行（P2） |
| `status` | 待办、进行中、待验收、完成、已取消 |
| `assignee` | 某个 Agent，或用户自己 |
| `projectId?` | 可以为空，开始时走无项目任务的目录（[PROJECTLESS-TASKS.md](PROJECTLESS-TASKS.md)） |
| `parentId?` | 子任务，只支持一层 |
| `labels` | 字符串数组 |

会话通过 `Session.workItemId` 挂到任务上，一个会话最多属于一个任务。分叉、交接出来的会话继承原会话的任务。任务的活动（创建、状态变化、挂上会话、评论、交付、提问、核对结论）记在 `work_item_events`。

### 4.3 从哪里来

| 来源 | 行为 |
| --- | --- |
| 看板上的「新建任务」 | 填标题、描述、执行者、项目，可选「创建后开始」 |
| 会话菜单的「转为任务」 | 把已有会话变成任务 |
| 助理主对话 | 用户说要做什么，助理派出任务（§5.1） |

输入框发出的会话不自动成为任务，侧边栏也不显示任务状态：没经过看板或助理的会话没有验收标准，跟进无从核对，只会让每个会话都多一个状态环。2026-11-15 前自动建的任务，没有评论、提问、交付、返工和子任务的，服务端启动时删除，会话保留。

## 5. 助理

助理本身（主对话、目录、运行时、记忆、工具）的设计在 [ASSISTANT.md](ASSISTANT.md)。这里只写它与任务看板有关的行为。

### 5.1 接活

- 用户在助理的主对话里说要做什么。一句话里说了几件事，助理就拆成几个任务，每个任务带上它推断的项目、执行者和验收标准。项目推断不出来就问。
- **改代码的任务先出计划卡片**，用户点「开始」才派出；只读的任务（调研、读代码回答问题）直接开始。卡片在助理输入框上方，列出助理建的、还在待办的任务；开始后离开卡片，标题点开是看板上的任务详情。用户也可以在对话里说「开始」，由助理开始。
- 计划卡片不阻塞对话：发出卡片后这一轮就结束，用户可以接着说别的。
- 项目里的工作不在主对话里做。用户问调研任务的结论时直接答；改了东西的任务不复述交付，指向任务编号。

### 5.2 跟进

- 跟进是助理的后台运行（[ASSISTANT.md](ASSISTANT.md) §7），和主对话用同一个 Agent，不出现在主对话里。
- 唤醒：任务下的会话停下（§3 的规则排除用户在场的情况），或者到了跟进自己约的时间。30 秒内的多个事件合并成一次唤醒。
- 主对话和任何客户端都能看到跟进做过什么：每个动作记在对应任务的活动里。

### 5.3 看板工具

- 走 Riffet MCP，只列给助理项目里的会话：`list_projects`、`task_list`、`task_get`、`task_create`（`start` 决定是否立即开始）、`task_start`、`task_comment`。不提供替用户回答审批、改设置、删除、推送的能力；给会话发消息、核对交付留给跟进（P3）。
- 服务端开始任务（`POST /api/work-items/:id/start`）：用执行者的默认设置开一条会话，以任务标题命名，第一条消息是简报，会话在创建它的同一次写入里挂到任务上，CLI 启动时就带着 `task_submit`、`task_ask`。已经有会话的任务拒绝再开，再开一个会话是用户在看板上的操作。

## 6. 执行者的两个工具与证据

属于任务的会话自动带上两个工具（Riffet MCP，只能操作自己所属的任务）：

| 工具 | 作用 |
| --- | --- |
| `task_submit` | 交付：总结，加上每条验收标准的说明 |
| `task_ask` | 提问：一个需要用户或跟进决定的问题，可以带选项。问完这一轮结束，回答作为下一条消息发进来 |

开始一个任务时，第一条消息是服务端拼好的简报：标题、描述、验收标准，以及之前会话的结论（改过的文件、跑过的命令、最后的回答）。这样换一个会话、换一个 Agent 也不用重新交代。生成方式复用分叉简报（`apps/server/src/orchestration/brief.ts`）。

**证据由服务端采集，不经过 Agent 转述。** 交付时，服务端附上：

- 改动的文件：会话（含子 Agent）编辑工具调用的路径，从上次交付算起；
- 跑过的命令和结果：取自会话日志的工具事件，同一条命令只留最后一次；每一步都只是查看的命令（`ls`、`cat`、`git diff` 这类）不算；
- 分支、PR 和 CI：通过现有的 Git 服务（未做）。

待验收区把执行者的说法和证据并排显示；说法有没有证据支撑，由跟进（P3）或用户判断，不靠文字匹配。执行者不支持 MCP 时没有这两个工具，交付和提问由跟进读会话来判断。

各后端命令结果的来源（2026-11-15 核对本机记录）：Codex、TraeX 有结构化的退出码；Claude Code 失败时输出以 `Exit code N` 开头；Antigravity 输出里有「exited with code N」；Cursor 部分带退出码；DSH、Droid 只有成功或失败。

## 7. 收件箱

只放三类事：

| 类别 | 例子 |
| --- | --- |
| 要你回答 | 审批、Agent 的提问、计划卡片 |
| 要你验收 | 待验收的任务，附核对结论和证据 |
| 推不动 | 跟进处理不了的停顿，附它的判断 |

- 每一条都能就地处理：回答、批准、完成、返工，不必打开会话。
- 顺序：要你回答的在前，因为不处理 Agent 就一直停着；要你验收的在后。同一类里等得久的在前。
- 手机推送只推收件箱里新出现的条目。

## 8. 约束：不做成 subagent

依据 Anthropic 的《Building agents: When to fold subagents into your main agent loop》（2026-10-22）：把一件事拆给多个 Agent，每次交接都会丢上下文，token 成倍增加；值得多开 Agent 的情形是核验、彼此独立的并行工作、权限分离。

- **一个任务由一个完整的会话做到底。** 不把一件事按角色拆给几个 Agent（写功能、写测试、审代码）。
- **助理不转述。** 用户和执行者直接对话；跟进只发「继续」、回答、返工意见。
- **结果不经摘要传递。** 任务详情直接链接会话和证据，不由助理复述执行者的结果。

## 9. 看板页

页面已实现（P1），代码在 `apps/web/src/app/work-items/`。按 [设计体系](design/system/README.md) 搭，不另起视觉。

- **位置。** 侧栏导航顺序：新会话、个人助理、搜索内容、**任务看板**、自动化、收藏夹、插件；行尾是收件箱的条数。地址 `/tasks`，自动化在 `/automations`。
- **页面。** `PageScaffold column="board"`（1200）。页头只有标题「任务看板」和「新建任务」。内容列顶部：左边是标题式 `Select` 切换项目，右边是筛选（执行者、标签）和看板 / 列表的 `Segmented`。
- **收件箱在列的上方**，是一张列表，为空时不显示。下面是待办、进行中、待验收、完成四列；完成只显示最近 7 天，已取消不进列。手机上只有列表。
- **卡片。** 编号、项目、实时标记；标题最多两行；标签用 `neutral` 的 `Badge`；底行是执行者标志、会话数、子任务进度、改动统计、时间。圆角 12，1px `line` 描边，不加阴影。拖到别的列即改状态。
- **状态图标** 是逐步填满的圆环，每个状态一种颜色：待办灰色虚线，进行中蓝色（与运行中的点同色，都是 Agent 在做），待验收琥珀色（与待确认同色，都在等你），完成绿色，已取消灰色。侧栏里属于任务的会话，标题前放这个圆环。任务开的会话以任务标题命名，不再取简报首行「任务 #N：…」。
- **任务详情** 是悬浮在看板上的侧边面板，宽 440，内缩 16，`shadow-peek`；手机上整页。点面板外的看板区域或按 Esc 收起，点另一张卡片则换成那张。描述按 Markdown 显示，点一下编辑。依次是：标题、属性（状态、执行者、项目、标签）、描述与验收标准、操作（开始、完成、返工、再开一个会话）、证据、会话、子任务、活动与评论。
- **新建任务** 是 `form` 档弹窗：标题、描述、执行者、项目、「创建后开始」。
- **会话信息里的任务。** 属于任务的会话，会话信息（桌面的弹层、手机的面板）的去处列表第一行是「任务 #N」，行尾是状态，点开回到看板并打开这个任务。页头不放任务标记。

详细的视觉取值见 [DECISIONS.md](design/DECISIONS.md) 2026-11-14 的条目和原型。

## 11. 数据与协议

已实现：

- **存储。** 表 `work_items` 和 `work_item_events`，用 `CREATE TABLE IF NOT EXISTS` 追加，不升数据库版本（`apps/server/src/work-items/store.ts`）。`sessions` 的 JSON 增加可选的 `workItemId`。
- **契约。** `packages/contracts/src/work-items.ts`；`Session.workItemId` 进了 zod schema 和移动端 fixtures。
- **接口。**
  - `GET /api/work-items`（ETag 为任务修订号；`/api/lists/stream` 的 `changed` 带 `workItems`）。
  - `POST /api/work-items`（客户端 `id` 幂等）、`PATCH`、`DELETE /api/work-items/:id`。
  - `GET /api/work-items/:id/events`、`POST /api/work-items/:id/comments`。
  - `POST /api/sessions/:id/work-item`（挂上、转为任务、移出）。
  - `POST /api/sessions` 可带 `workItemId`；不带时按设置建任务，与会话在同一事务里创建，重试找回同一个任务。
- **分层。** 模块 `apps/server/src/work-items/` 在 features 层，路由 `routes/work-items.ts`，会话创建的接线在 `routes/sessions.ts`，分叉、交接的继承在 `store.ts`。Web 在 `apps/web/src/app/work-items/` 和 `state/workItemsStore.ts`。
- **兼容。** 旧客户端看不到任务；老服务端没有 `/api/work-items` 时，Web 隐藏任务看板入口。

P2 已加：

- `WorkItem.criteria`、`questions`（未回答的提问）、`submission`（最近一次交付，带证据）；事件 `submit`、`question`、`answer`、`rework`。
- Riffet MCP 的 `task_submit`、`task_ask`：只列给属于任务的会话（CLI 启动时的状态）；证据在 `work-items/evidence.ts`，从会话日志（`journal_events`，含子 Agent 的分支）里的工具调用读取。

- 跟进的唤醒在 work-items 模块订阅会话状态变化（`work-items/supervision.ts`），不进调度器核心；运行本身是助理的后台运行（`assistant/runs.ts`，[ASSISTANT.md](ASSISTANT.md) §7）。
- `WorkItem.stuck`（推不动，附跟进的判断），收件箱的第三类；会话再次运行或用户在任务上有动作时清掉。跟进核对通过的交付不标推不动，结论记为任务的评论。
- 事件 `nudge`（跟进发的「继续」或回答）、`stuck`，`rework` 增加 `by: 'assistant'`。连续两次推动没有进展的判断在 `WorkItemService.pushesWithoutProgress`：其间没有交付、回答、用户的返工或状态变化，任务的会话里也没有用户自己发的消息。

## 12. 分期

| 期 | 范围 | 验收 |
| --- | --- | --- |
| P1 | 任务、看板、任务详情、自动建任务、会话挂接与继承。Web 已完成 | 新建任务后看板出现卡片，状态随会话变化；分叉的会话挂在原任务下 |
| P2 任务闭环 | 验收标准、简报、`task_submit` 与 `task_ask`、服务端证据、收件箱三类与就地处理、两个北极星指标；Mac 补齐 P1 | 带两条验收标准的任务开始后，执行者交付，待验收里有逐条说明和服务端采集的命令与退出码；统计页能看到每天打扰次数和等待时长 |
| P3 跟进 | 后台跟进、唤醒与合并、用户在场时让路、核对与返工、推动停下的会话、推不动进收件箱 | 用户离开后，一个停在中间的会话被跟进推动并完成；一个不合格的交付被退回一次后通过；打扰次数低于 P2 |
| P4 助理主对话 | 助理页、拆任务与计划卡片、手机首页改成助理 | 在手机上一句话派出两个任务，最后只在验收时被打扰 |

核心测试只覆盖：任务与会话的幂等创建和继承、只有用户能改成完成、证据由服务端采集、跟进在用户在场时不唤醒、数据库迁移。界面不加展示类测试。
