# Riffet 任务看板与助理

日期：2026-11-16（初稿 2026-11-13）。状态：P1、P2 的服务端与 Web 已实现（Mac 未开始）；P4 助理主对话的服务端与 Web 已实现，助理本身的设计移到 [ASSISTANT.md](ASSISTANT.md)；P3 跟进的服务端与 Web 已实现（[ASSISTANT.md](ASSISTANT.md) §7.2）。交互原型：[design/task-board-demo.html](design/task-board-demo.html)。

## 1. 问题与目标

**问题。** 用户同时推进很多件事。Agent 每做完一轮就停下，用户得自己在会话之间找，判断它做完没有、下一步该做什么。

本机最近 14 天的记录（2026-11-01 至 11-14，不含快速对话）：

- 319 个会话分布在 15 个项目里，平均每天动 20 多个。
- 有 Agent 在跑的时间里，43% 同时跑着两个以上。
- 用户连续发出的两条消息，72% 不在同一个会话。
- 一轮结束后，用户回到这个会话的间隔：中位数 5 分钟，四分之一超过 19 分钟，十分之一超过 1.5 小时。

**目标。** 少打扰用户，少让 Agent 等用户。用两个数衡量，显示在统计页：

| 指标 | 算法 |
| --- | --- |
| 每天打扰次数 | 一天里送到用户面前、需要用户处理的条目数：审批、提问、待验收、推不动的事 |
| Agent 等用户的时长 | 会话停下等用户处理的总时长，从停下算到用户处理为止 |

每一项设计都要说明它降低了哪个数。降不了的不做。

记录方式：会话进入「等你确认」或一轮结束停下时，服务端在 `attention_log` 记一笔开始时间，会话再动起来、或它所属的任务被标为完成时，补上结束时间（`apps/server/src/work-items/attention.ts`）。提问和待验收从任务活动里数。还没结束的等待不计入；会话没人回来就归档了，这一笔删掉。开始记录之前的日子显示为未知，不算作 0。

## 2. 概念

只有三个新概念。会话保持现状，不改名，不改界面。

| 概念 | 是什么 |
| --- | --- |
| 任务 | 一件要做成的事。下面挂着做它的会话，有自己的状态和验收标准。代码名 `WorkItem` |
| 助理 | 用户的常驻 Agent（[ASSISTANT.md](ASSISTANT.md)）。与看板有关的是两部分：**主对话**，用户在这里说要做什么，它派出任务；**跟进**，在后台盯着进行中的任务，不占主对话 |
| 收件箱 | 唯一会打扰用户的地方。只放要用户决定的事 |

## 3. 流程

```
┌──────┐              ┌────────┐               ┌────────┐
│  你  │ ──说要什么─▶ │  助理  │ ──派任务──▶  │  会话  │
└──────┘              └────────┘               └────────┘
    ▲                                               │
    │                                               │ 停下
    │                                               ▼
┌──────────┐                               ┌────────────────┐
│  收件箱  │ ◀───────只在要你决定时─────── │  跟进（后台）  │
└──────────┘                               └────────────────┘
```

任务也可以由用户自己建：在看板上新建，或者把已有会话转为任务。之后的流程相同。

会话停下时，跟进按下表处理：

| 会话停下的情况 | 跟进做什么 |
| --- | --- |
| 执行者交付了 | 对照验收标准核对证据（§6）。通过，进收件箱等用户验收；不通过，把具体问题作为返工意见发回会话 |
| 在等审批，或在问用户 | 直接进收件箱。审批只由用户回答 |
| 出错，或停在中间、没有说明 | 读这个会话：能推就推（让它继续、回答它自己能答的问题、到点再看）；推不动才进收件箱 |

跟进判断的依据：

1. 会话自己的状态：在跑、等审批或提问、出错。
2. 执行者的汇报：交付或提问（§6）。
3. 前两者都没有时，跟进才读这个会话的内容。

两条规则保证跟进不碍事：

- **用户在场时不插手。** 用户 10 分钟内在某个会话里发过消息，跟进就不处理这个会话。用户离开后会话停下了，才轮到跟进。
- **不改代码，不转述。** 跟进发给会话的只有三种消息：「继续」、对问题的回答、返工意见。用户随时可以直接进会话说话。

推不动的界限：同一个任务连续推了两次还没有进展，或者返工两轮仍不通过，就进收件箱，附上跟进的判断。

## 4. 任务

### 4.1 状态

```
 看板上新建                         看板上新建并开始，或转为任务     
     │                                           │
     ▼                                           ▼
┌────────┐                        ┌──────────────────────────────┐
│  待办  │ ──── 开始（你）─────▶  │            进行中            │
└────────┘                        │                              │
                                  │  运行中                      │
                                  │  等你：审批、提问            │
                                  │  失败                        │
                                  │  空闲：回合结束、没交付      │
                                  └──────────────────────────────┘
                                      │ ▲
                       交付（执行者） │ │ 返工（你或跟进）
                                      ▼ │
                                  ┌──────────────────────────────┐
                                  │            待验收            │
                                  └──────────────────────────────┘
                                      │
                       验收（只有你） │
                                      ▼
                                  ┌──────────────────────────────┐
                                  │             完成             │
                                  └──────────────────────────────┘
```

- 方框是存储的状态。「进行中」框里的四行是实时标记，从会话状态推导，不存储，规则在 `packages/contracts/src/session-attention.ts`。
- 跟进上线后，交付先经跟进核对，通过了才进待验收。
- **观测中**（`watching`）：暂时不推进、等待时间或外部条件；后台跟进跳过此状态。可设「观测备注」「到期提醒」（到点自动浮回收件箱），或绑定一条个人助理委托（网页变化、GitHub 发版、定时巡检）；底下的会话若有审批或提问仍会回到收件箱。
- 用户可以把卡片拖到任何一列或观测区；没结束的任务可以标为**无需关注**（`cancelled`，与完成一起进入终态历史）；完成或无需关注后再开会话，任务回到进行中。
- **只有用户能改成完成。**

### 4.2 字段

| 字段 | 说明 |
| --- | --- |
| `number` | 服务器内递增，显示为 `#128`。任务可以跨项目，所以不按项目分号 |
| `title`、`description` | 描述是 Markdown |
| `criteria` | 验收标准，一条一行（P2） |
| `status` | 待办、进行中、观测中、待验收、完成、无需关注 |
| `watch?` | 观测设置：`until`（到期浮回时间）、`note`（观测备注）、`delegationId`（关联委托） |
| `assignee` | 某个 Agent（可带提供商和模型，开会话时照用；不带时用这个 Agent 的默认设置），或用户自己 |
| `projectId?` | 可以为空，开始时走无项目任务的目录（[PROJECTLESS-TASKS.md](PROJECTLESS-TASKS.md)） |
| `parentId?` | 子任务，只支持一层 |
| `blockedBy?` | 前置任务：要先完成的任务（§4.4），最多 10 个 |
| `labels` | 字符串数组 |

会话通过 `Session.workItemId` 挂到任务上，一个会话最多属于一个任务。交接出来的会话继承原会话的任务；分叉出来的会话另建一个任务（同「转为任务」，跟随会话标题，进行中），两边状态互不影响，原会话不属于任务时分叉也不建。任务的活动（创建、状态变化、挂上会话、评论、交付、提问、核对结论）记在 `work_item_events`。

### 4.3 从哪里来

| 来源 | 行为 |
| --- | --- |
| 看板上的「新建任务」 | 写要做什么，选执行者（Agent 与模型）和项目，可加完成标准；「加入待办」或「开始」 |
| 会话菜单的「转为任务」 | 把已有会话变成任务 |
| 助理主对话 | 用户说要做什么，助理派出任务（§5.1） |

输入框发出的会话默认不成为任务：没经过看板或助理的会话没有完成标准，跟进只能读会话来判断，而且每个会话都会多一个状态环。设置「任务看板」页的「新会话作为任务」打开后，从输入框开的会话（快速对话、个人助理除外）同时建一个进行中的任务，标题跟随会话标题，执行者是会话所用的 Agent 与模型。2026-11-15 前自动建的任务，没有评论、提问、交付、返工和子任务的，服务端首次启动时删除一次，会话保留。

### 4.4 前置任务

一件事要分几步、后一步用到前一步的结果时（先定接口再实现，先迁移再改调用方），后一步把前一步设为前置任务。互不依赖的任务不设，它们可以同时做。这是 Riffet 对「多个 Agent 一起做一件事」的回答：每一步仍是一个任务、一个完整的会话（§8），前后顺序由服务端按规则推进，不由某个 Agent 拆分和转交。

- **开始。** 前置任务还没全部完成时点「开始」，任务进入进行中并记下「要开始」（`startQueued`），但不开会话；最后一个前置任务完成时，服务端用执行者的设置开第一个会话（与 §5.3 的服务端开始相同）。只有点过「开始」的才会自动开工：把卡片拖到进行中不算；挂上会话或离开进行中时这个标记清掉。只有「完成」算完成：待验收的还要等用户验收，免得后一步建在没验收的结果上。
- **简报。** 简报多一节「前置任务」：每个前置任务的标题、最近一次交付的说明和改动的文件。
- **不推进的情况。** 等待中的任务，前置任务被标为无需关注（包括点「开始」时它已经是），或者开会话失败，任务进收件箱的「推不动」，附原因，由用户决定：去掉这个前置任务就会开始，也可以直接改任务。
- **约束。** 不能等自己，不能互相等（服务端拒绝成环）。删掉一个任务时，它从别人的前置任务里去掉；等它的任务因此没有前置了，就开始。服务端重启后，把前置已全部完成、还在等的任务各开一次。
- 只在待办或进行中设置有意义；已经有会话的任务改前置任务不影响它。

## 5. 助理

助理本身（主对话、目录、运行时、记忆、工具）的设计在 [ASSISTANT.md](ASSISTANT.md)。这里只写它与任务看板有关的行为。

### 5.1 接活

- 用户在助理的主对话里说要做什么。一句话里说了几件事，助理就拆成几个任务，每个任务带上它推断的项目、执行者和验收标准。项目推断不出来就问。
- **改代码的任务先出计划卡片**，用户点「开始」才派出；只读的任务（调研、读代码回答问题）直接开始。卡片在助理输入框上方，列出助理建的、还在待办且未收起的任务；点「开始」、点标题打开看板上的任务详情，或点行尾「移除」后离开卡片（手动移除或查看详情的任务仍留在看板的「待办」中）。用户也可以在对话里说「开始」，由助理开始。
- 计划卡片不阻塞对话：发出卡片后这一轮就结束，用户可以接着说别的。
- 项目里的工作不在主对话里做。用户问调研任务的结论时直接答；改了东西的任务不复述交付，指向任务编号。

### 5.2 跟进

- 跟进是助理的后台运行（[ASSISTANT.md](ASSISTANT.md) §7），和主对话用同一个 Agent，不出现在主对话里。
- 唤醒：任务下的会话停下（§3 的规则排除用户在场的情况），或者到了跟进自己约的时间。30 秒内的多个事件合并成一次唤醒。
- 主对话和任何客户端都能看到跟进做过什么：每个动作记在对应任务的活动里。

### 5.3 看板工具

- 走 Riffet MCP，只列给助理项目里的会话：`list_projects`、`task_list`、`task_get`、`task_create`（`start` 决定是否立即开始）、`task_start`、`task_comment`。不提供替用户回答审批、改设置、删除、推送的能力；给会话发消息、核对交付留给跟进（P3）。
- 服务端开始任务（`POST /api/work-items/:id/start`）：用执行者的默认设置开一条会话，以任务标题命名，第一条消息是简报，会话在创建它的同一次写入里挂到任务上，CLI 启动时就带着 `task_submit`、`task_ask`。已经有会话的任务拒绝再开，再开一个会话是用户在看板上的操作。前置任务没完成时只排队，返回里没有 `sessionId`（§4.4）。
- `task_create` 的 `after` 填前置任务的编号；`riffet:tasks` 写明只在后一步要用到前一步的结果时才填。

## 6. 执行者的两个工具与证据

属于任务的会话自动带上两个工具（Riffet MCP，只能操作自己所属的任务）：

| 工具 | 作用 |
| --- | --- |
| `task_submit` | 交付：总结，加上每条验收标准的说明 |
| `task_ask` | 提问：一个需要用户或跟进决定的问题，可以带选项。问完这一轮结束，回答作为下一条消息发进来 |

开始一个任务时，第一条消息是服务端拼好的简报：标题、描述、验收标准，以及之前会话的结论（改过的文件、跑过的命令、最后的回答）。这样换一个会话、换一个 Agent 也不用重新交代。生成方式复用分叉简报（`apps/server/src/orchestration/brief.ts`）。

**证据由服务端采集，不经过 Agent 转述。** 交付时，服务端附上：

- 改动的文件：会话（含子 Agent）编辑工具调用的路径，从上次交付算起；
- 跑过的命令和结果：取自会话日志的工具事件，同一条命令只留最后一次；每一步都只是查看的命令（`ls`、`cat`、`git diff` 这类）不算；
- 分支、PR 和 CI：通过现有的 Git 服务（未做）。

待验收区把执行者的说法和证据并排显示；说法有没有证据支撑，由跟进（P3）或用户判断，不靠文字匹配。执行者不支持 MCP 时没有这两个工具，交付和提问由跟进读会话来判断。

### 6.1 核验

设置「任务看板」页的「核验」选一个 Agent（可带提供商和模型）后，每次交付都由它只读地检查一遍，结论附在任务上。默认不核验。用另一个 Agent 核验，是业界公认多开 Agent 有价值的情形之一，也是并行之后最大的瓶颈（验收）所在。

- **怎么跑。** 交付后，服务端以交付的会话的名义开一次只读咨询（[Agent 调用](AGENT-CALLS.md) 的 `consult`，在交付的会话所在的目录里）：第一条消息是任务、验收标准、执行者的说法和服务端证据，要求它看仓库里的实际改动，第一行写「结论：通过 / 不通过 / 无法判断」。它在交付的会话的「调用」里，用户能打开、旁观、插话。
- **结论去哪。** 只进任务（`WorkItem.verification` 与 `verify` 事件），**不发回执行者**：返工意见只由用户或跟进发。待验收卡和任务详情显示结论，详情里能读全文、打开核验的会话。
- **和跟进的关系。** 跟进打开时，在核验结束后才看这次交付，并以核验结论为主要依据：不通过就把它指出的问题作为返工意见发回。核验停在审批上时跟进不再等它。跟进关着时，结论只给用户验收时看。
- 执行者自己的 `agent_list`、`agent_wait`、`agent_stop` 看不到也碰不到核验的会话。
- 新的交付会开新的核验，旧的那次结束后不再记录；核验正在开出时又交付了，开出后再为最新的交付开一次。核验开不起来（这个 Agent 不支持只读咨询、不可用）时记为核验失败，附原因。
- 每次交付多跑一个会话，用量计在所选的 Agent 上。

各后端命令结果的来源（2026-11-15 核对本机记录）：Codex、TraeX 有结构化的退出码；Claude Code 失败时输出以 `Exit code N` 开头；Antigravity 输出里有「exited with code N」；Cursor 部分带退出码；DSH、Droid 只有成功或失败。

## 7. 收件箱

只放三类事：

| 类别 | 例子 |
| --- | --- |
| 要你回答 | 审批、Agent 的提问、计划卡片、插件请你确认的写操作 |
| 要你验收 | 待验收的任务，附核对结论和证据 |
| 推不动 | 跟进处理不了的停顿，附它的判断 |

- 每一条都能就地处理：回答、批准、完成、返工，不必打开会话。
- 顺序：要你回答的在前，因为不处理 Agent 就一直停着；要你验收的在后。同一类里等得久的在前。
- 手机推送只推收件箱里新出现的条目。
- **插件审批。** 进程内的插件用 `host.approvals.request` 把一次待执行的写操作放进收件箱，在任意客户端点按钮确认，选择交给插件的 `approvals.decide` 去执行（SDK 见 [插件架构](PLUGIN_ARCHITECTURE.md)「收件箱审批」）。它是要你回答的一个来源，排在任务相关条目之前，同类里先请求的在前；行里是标题、插件名、折叠的 Markdown 正文和按钮，`danger` 语气的按钮用危险按钮样式。服务端持久保存（重启后仍在），到 `expiresAt`、被插件撤回、插件停用或卸载时消失；`decide` 报错时错误显示给用户、条目保留，成功后条目移除。每个插件同时打开的条数有上限（`PLUGIN_APPROVAL_BUDGET`）。新条目像其他收件箱条目一样推到手机，推送不属于任何会话，只提示有一条待处理。

## 8. 约束：不做成 subagent

依据 Anthropic 的《Building agents: When to fold subagents into your main agent loop》（2026-10-22）：把一件事拆给多个 Agent，每次交接都会丢上下文，token 成倍增加；值得多开 Agent 的情形是核验、彼此独立的并行工作、权限分离。

- **一个任务由一个完整的会话做到底。** 不把一件事按角色拆给几个 Agent（写功能、写测试、审代码）。
- **助理不转述。** 用户和执行者直接对话；跟进只发「继续」、回答、返工意见。
- **结果不经摘要传递。** 任务详情直接链接会话和证据，不由助理复述执行者的结果。

页面已实现（P1），代码在 `apps/web/src/app/work-items/`。按 [设计体系](design/system/README.md) 搭，不另起视觉。

- **位置。** 侧栏导航顺序：新会话、个人助理、搜索内容、**任务看板**、自动化、收藏夹、插件；行尾是收件箱的条数。地址 `/tasks`，自动化在 `/automations`。
- **页面。** `PageScaffold column="board"`（1200）。页头只有标题「任务看板」和「新建任务」。内容列顶部：左边是标题式 `Select` 切换项目，右边是筛选（执行者、标签）和看板 / 列表的 `Segmented`。
- **任务概览。** 工具栏下方用一张卡展示近 14 天的新建与完成趋势，侧栏展示任务总数和六种状态的数量与占比，标题旁展示收件箱、运行中的任务及关联会话数。趋势按本地日期展示创建量和当前已完成任务的最近完成日期。以上数字跟随项目、执行者、标签及搜索，统计包括完成列默认折叠或隐藏的历史任务。
- **收件箱在列的上方**，是一张列表，为空时不显示；**观测中**在收件箱与四列之间，可折叠并支持拖入拖出。下面是待办、进行中（按活跃与停下分层）、待验收、完成（含最近 7 天完成的任务和「无需关注」）四列，完成列默认折叠超出最近 10 条的部分；搜索时可命中更早的已收口任务。手机上只有列表。
- **收件箱与观测中的行尾**共用状态说明、执行者及时间列，窄屏把行尾挪到标题下方。悬停或聚焦时，快捷操作在时间列原位显示，触屏直接显示操作。
- **卡片。** 列与圆角 12 的实底卡按[看板任务卡规范](design/system/patterns.md#看板任务卡)分层。标题最多两行，编号和项目在顶部，执行者、会话数、子任务进度和时间在底部。标签用 `neutral` 的 `Badge`，待验收卡附带标准命中与改动文件线索。快捷操作在时间原位出现，拖到别的列即改状态。
- **状态图标** 是逐步填满的圆环，每个状态一种颜色：待办灰色虚线，进行中蓝色（与运行中的点同色，都是 Agent 在做），观测中中性灰环中心带点，待验收琥珀色（与待确认同色，都在等你），完成绿色，无需关注灰色斜杠圆。侧栏里属于任务的会话，标题前放这个圆环；会话运行中时外圈断开成弧并旋转，代替行首的 `Spinner`，任务看板的列表行同理。任务开的会话以任务标题命名，不再取简报首行「任务 #N：…」。
- **任务详情** 是悬浮在看板上的侧边面板，宽 440，内缩 16，`shadow-peek`；手机上整页。点面板外的看板区域或按 Esc 收起，点另一张卡片则换成那张。描述按 Markdown 显示，点一下编辑。依次是：标题、属性（状态、执行者、项目、标签）、描述与验收标准、操作（开始、完成、返工、再开一个会话）、证据、会话、子任务、活动与评论。
- **新建任务** 是 `form` 档弹窗，从上到下：
  - 一个多行输入框写要做什么，一句话也行。第一行是标题（超出长度截断，全文进描述），其余是描述；标题之后在详情里改。
  - 「完成标准」默认收起，点开是一个多行输入框，一条一行，下面一句说明「Agent 交付时逐条说明，由你验收」。
  - 一行两个选择：执行者用输入框同一个模型按钮（Agent、提供商、模型），默认取设置「任务看板」页的默认 Agent 与模型；项目用 `Select`。交给自己的任务在详情里改执行者。
  - 页脚「加入待办」（`secondary`）和「开始」（`primary`），不再用「创建后开始」勾选框。
- **会话信息里的任务。** 属于任务的会话，会话信息（桌面的弹层、手机的面板）的去处列表第一行是「任务 #N」，行尾是状态，点开回到看板并打开这个任务。页头不放任务标记。

详细的视觉取值见 [DECISIONS.md](design/DECISIONS.md) 2026-11-14 的条目和原型。

Mac：M，概览随 `/tasks` 在 Web 查看。插件审批同属收件箱：Web 已列出，Mac 与 Android、iOS 目前没有收件箱页面，待收件箱进菜单栏与通知（[Mac 范围规范](guide/mac-scope.md) §5 第 5 项）和手机的任务页时一并接入 `GET /api/plugin-approvals`。

### 多服务器

- 任务属于 A 类工作对象。概览和搜索读取同一份任务列表；现有列表只读取入口服务器的任务。链接支持落地后，概览随任务列表合并各服务器的数据并沿用该列表的离线与版本提示。
- 概览只在客户端派生数字，请求与操作沿用看板的数据层。无新增路由、对象、编号、协议字段、缓存、提醒、插件扩展点或 MCP 工具。经链接的权限沿用任务接口。

## 11. 数据与协议

已实现：

- **存储。** 表 `work_items` 和 `work_item_events`，用 `CREATE TABLE IF NOT EXISTS` 追加，不升数据库版本（`apps/server/src/work-items/store.ts`）。`sessions` 的 JSON 增加可选的 `workItemId`。
- **契约。** `packages/contracts/src/work-items.ts`；`Session.workItemId` 进了 zod schema 和移动端 fixtures。
- **接口。**
  - `GET /api/work-items`（ETag 为任务修订号；`/api/lists/stream` 的 `changed` 带 `workItems`）。
  - `POST /api/work-items`（客户端 `id` 幂等）、`PATCH`、`DELETE /api/work-items/:id`。
  - `GET /api/work-items/:id/events`、`POST /api/work-items/:id/comments`。
  - `POST /api/sessions/:id/work-item`（挂上、转为任务、移出）。
  - `POST /api/sessions` 可带 `workItemId`；不带时按设置建任务，与会话在同一事务里创建，重试找回同一个任务。
- **分层。** 模块 `apps/server/src/work-items/` 在 features 层，路由 `routes/work-items.ts`，会话创建的接线在 `routes/sessions.ts`，交接的继承在 `store.ts`，分叉另建任务在 `routes/orchestration.ts`。Web 在 `apps/web/src/app/work-items/` 和 `state/workItemsStore.ts`。
- **兼容。** 旧客户端看不到任务；老服务端没有 `/api/work-items` 时，Web 隐藏任务看板入口。

P2 已加：

- `WorkItem.criteria`、`questions`（未回答的提问）、`submission`（最近一次交付，带证据）；事件 `submit`、`question`、`answer`、`rework`。
- Riffet MCP 的 `task_submit`、`task_ask`：只列给属于任务的会话（CLI 启动时的状态）；证据在 `work-items/evidence.ts`，从会话日志（`journal_events`，含子 Agent 的分支）里的工具调用读取。
- `GET /api/work-items/north-star?from&to&tz`：北极星的逐日数字。
- `GET /api/work-items/:id/brief`（开工简报）、`POST /api/work-items/:id/questions/:questionId/answer`、`POST /api/work-items/:id/rework`；回答和返工意见作为普通消息发进会话，`commandId` 保证只发一次。

P4 已加：

- `Project.system` 增加 `assistant`，`WorkItem.source` 增加 `assistant`；助理项目里的会话不自动建任务，也不能挂到任务上。
- `POST /api/work-items/:id/start`；Riffet MCP 的助理工具在 `riffet-mcp/service.ts`，具体操作在 `work-items/assistant.ts`。
- Web：侧栏导航的「个人助理」入口与助理页（[ASSISTANT.md](ASSISTANT.md) §3；2026-11-16 前是新会话页的页签）、计划卡片 `work-items/PlanDock.tsx`。
- 助理配置：`AppSettings.assistant`（Agent、Provider、模型）；`GET/PUT /api/assistant/instructions`；首页卡片 `work-items/AssistantSetup.tsx`。
- 任务开的会话以任务标题命名；之前取了「任务 #N：…」的会话，服务端启动时去掉前缀（`WorkItemService.retitleBriefConversations`）。

插件审批已加：

- 表 `plugin_approvals`（同一个工作台数据库，`CREATE TABLE IF NOT EXISTS`），服务在 `apps/server/src/plugins/approvals.ts`，路由 `routes/plugin-approvals.ts`：`GET /api/plugin-approvals`、`POST /api/plugin-approvals/:pluginId/:id/decide`（body `{ actionId }`，成功返回 `{ message? }`，条目不存在或已过期 404）。变化经 `/api/lists/stream` 的 `plugin-approvals` 事件通知。契约在 `packages/contracts/src/plugins.ts`。
- 作用范围 `global`：链接策略对 `/api/plugin-approvals` 一律拒绝，客户端只读入口服务器的条目。

P3 已加：

- 跟进的唤醒在 work-items 模块订阅会话状态变化（`work-items/supervision.ts`），不进调度器核心；运行本身是助理的后台运行（`assistant/runs.ts`，[ASSISTANT.md](ASSISTANT.md) §7）。
- `WorkItem.stuck`（推不动，附跟进的判断），收件箱的第三类；会话再次运行或用户在任务上有动作时清掉。跟进核对通过的交付不标推不动，结论记为任务的评论。
- 事件 `nudge`（跟进发的「继续」或回答）、`stuck`，`rework` 增加 `by: 'assistant'`。连续两次推动没有进展的判断在 `WorkItemService.pushesWithoutProgress`：其间没有交付、回答、用户的返工或状态变化，任务的会话里也没有用户自己发的消息。

P5 已加：

- `WorkItem.blockedBy`（创建与修改都可带，`null` 清空）与 `WorkItem.startQueued`，校验与推进在 `WorkItemService`：`requireBlockers` 拒绝自指、不存在和成环；任务状态变化后 `releaseDependents` 开会话或标推不动；启动 15 秒后 `resumeWaiting`。`POST /api/work-items/:id/start` 的返回是 `WorkItemStartResult`，排队时没有 `sessionId`。客户端用契约里的 `openPrerequisites` 判断还在等哪些。
- `WorkItem.verification`、事件 `verify`、设置 `AppSettings.workItems.verifier`。触发与收尾在 `work-items/verification.ts`（订阅交付、被调用会话的停止和回合结束），开会话用 `AgentCallService.consultFor`：调用记录在开出时就标为已送达，所以不会交还给调用方。跟进经 `Supervision` 的 `verifying` 等核验结束，结束后 `checked` 再看一次。核验的第一条消息在 `prompts/task-verify.md`。

## 12. 分期

| 期 | 范围 | 验收 |
| --- | --- | --- |
| P1 | 任务、看板、任务详情、自动建任务、会话挂接与继承。Web 已完成 | 新建任务后看板出现卡片，状态随会话变化；交接的会话挂在原任务下，分叉的会话有自己的任务 |
| P2 任务闭环 | 验收标准、简报、`task_submit` 与 `task_ask`、服务端证据、收件箱三类与就地处理、两个北极星指标。Mac 按 [范围规范](guide/mac-scope.md) 处理：看板页先给打开 Web 的入口，收件箱进菜单栏与通知（规范 §5 第 5 项） | 带两条验收标准的任务开始后，执行者交付，待验收里有逐条说明和服务端采集的命令与退出码；统计页能看到每天打扰次数和等待时长 |
| P3 跟进 | 后台跟进、唤醒与合并、用户在场时让路、核对与返工、推动停下的会话、推不动进收件箱 | 用户离开后，一个停在中间的会话被跟进推动并完成；一个不合格的交付被退回一次后通过；打扰次数低于 P2 |
| P4 助理主对话 | 助理页、拆任务与计划卡片、手机首页改成助理 | 在手机上一句话派出两个任务，最后只在验收时被打扰 |
| P5 前后步与核验 | 前置任务（§4.4）、另一个 Agent 核验交付（§6.1）。服务端与 Web | 派出「定接口」和「实现」两个任务，实现排在接口之后；接口验收完成后实现自动开始，简报里有接口的交付；实现交付后，核验的结论出现在待验收卡上 |

核心测试只覆盖：任务与会话的幂等创建和继承、只有用户能改成完成、证据由服务端采集、跟进在用户在场时不唤醒、前置任务完成后只开一次会话、核验的结论不交还给执行者、数据库迁移。界面不加展示类测试。

## 13. 参考

| 项目 | 取 | 不取 |
| --- | --- | --- |
| [Persona](https://github.com/nwverse/persona) | 用打扰次数衡量；一个主对话接意图，跟进在后台；交付要逐条附证据，不自动结束；用户在说话时系统消息排队；审批不代答 | 学规则、多级跟进、按会话分诊等大量细则 |
| [multica](https://github.com/multica-ai/multica) | 任务是长期记录，会话是一次执行；Agent 自己汇报和交付；拆分的标准 | 团队、小队、自定义状态与工作流 |
| [OpenClaw](https://github.com/openclaw/openclaw)、[Hermes Agent](https://github.com/NousResearch/hermes-agent) | 用户能直接进入执行的会话；交付以外部证据为准（Hermes 要求 CI 通过）；Hermes Kanban 把交接做成人能看、能改的看板数据 | 子 Agent 只交回摘要、父 Agent 复述结果：两边的 issue 里都出现了丢上下文、丢结果；多个身份（OpenClaw 的多 agent、Hermes 的 profile）：价值在隔离，不在提升结果（[ASSISTANT.md](ASSISTANT.md) §11） |
| [Claude Code agent teams](https://code.claude.com/docs/en/agent-teams) | 共享的任务列表带依赖；适用的是互不相交的模块和核验 | lead 拆分并汇总、成员互发消息：实验特性，官方列出的问题是 lead 提前收尾、状态滞后、同文件冲突 |
| Anthropic《multi-agent research system》、Cognition《Don't Build Multi-Agents》 | 多开 Agent 只在广度并行、核验、权限分离时值得；成本数倍 | 默认拆分给多个 Agent |
