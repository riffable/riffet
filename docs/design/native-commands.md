# 原生命令接入与状态确认

## 问题与范围

Codex App Server 不会把普通消息中的 `/compact` 解释成压缩操作。此前 Riffet 只解析技能，其余斜杠输入进入 `turn/start`，模型可能回复已完成，但没有对应的原生操作。技能目录读取失败时也会丢失结构化技能输入。

本轮完成 Codex 的压缩与 Review 接入、命令和技能的失败处理、Review 结果投影，以及 Codex/TRAE 共用的压缩状态修正。Claude Code、Cursor 的终端命令转发、Droid、pi、DeepSeek Harness 的既有协议保持各自语义。

## 命令与执行

| 输入 | 原生操作 | 约束 |
| --- | --- | --- |
| `/compact` | `thread/compact/start` | 不接受附加指令 |
| `/review` | `review/start`，`uncommittedChanges` | 在当前线程执行 |
| `/review <审查要求>` | `review/start`，`custom` | 原样传递审查要求 |
| `/技能名` | `turn/start` 的结构化 `skill` 输入 | 必须是已启用技能 |

原生命令不接受附件、文件上下文和会话引用，避免忽略用户添加的材料。Codex/TRAE 的行首斜杠项既不是可执行命令，也不是已启用技能时，发送失败。目录查询失败时，行首调用和该项目／配置中已确认过的技能引用保留明确错误；从未识别为技能的行内 `/health` 等按文字处理，不让普通 API 路径依赖技能目录可用性。模型、模式和权限继续使用已有会话控件。

原生命令继承线程设置，没有普通 `turn/start` 的逐轮配置字段。通过 `thread/settings/update` 一次提交模型、权限、沙箱和明确选择的 effort／tier，其空响应仅表示已接收。随后用不携带覆盖参数的 `thread/resume` 读取实际配置，核对线程、目录、模型、权限和完整沙箱；缺字段、不一致或超时都在派发命令前失败。所有线程均经过核验，未单独选模型的会话沿用配置的默认模型。

从配置准备开始记录设置通知；期间出现不兼容的配置变化时，即使后续读取又匹配也拒绝执行。设置核验后到命令发送之间不再等待其他 I/O，并检查已观察到的配置变化。原生协议没有原子的“配置匹配才执行命令”操作，因此无法保证其他独立客户端在最后间隔内不修改配置。

## 派发与回执

复用 NativeDispatcher、Run、session lock、dispatch fence 和 Journal，不增加命令任务表或第二套队列。

1. 在不可重放的派发标记写入前校验参数、连接与忙碌状态。
2. 记录派发标记后只发出一次原生 RPC。失败后不改发普通消息，不自动重发。
3. Review 使用返回的线程和回合 ID 绑定。压缩的空响应只表示请求已接受；候选必须有派发后独立收到的 `turn/started`，没有用户消息且包含压缩事件。派发前已知的结束回合、包括尚未关联 Riffet Run 的回合，都排除在候选外。
4. 绑定后通过 `host.emitEvent` 发出 `native_input_receipt`，由派发器持久化回合关联。
5. Run 的最终状态来自 Journal 的原生回合结束记录。接口返回、压缩 item 结束和空闲状态均不单独结算 Run。先完成后收到回执，以及派发器重建后的完成恢复，沿用现有逻辑。

压缩协议不提供请求关联 ID，无法完全区分其他客户端同时提交的手动压缩。出现多个候选、用户回合、超时或断线时保持未确认，不猜测归属。绑定等待有期限；停止操作可先释放本地等待，再取得会话锁执行原生停止。尚未绑定的命令不能被推断为已取消，但可以停止用户明确指定的已知回合；派发器仅结算该回合，保留其他未确认输入。

原生 RPC 的结果监听独立于本地等待。即使 Stop 已结束等待，迟到的明确拒绝仍通过 `native_input_rejected` 到达派发器。派发器核对会话、命令、后端和派发标记后记录失败，不给无回合的拒绝伪造回合 ID。迟到的 Review 响应携带明确回合 ID，可按原始请求恢复绑定。

## 展示与状态

Review 的进入事件映射为过程记录，退出事件映射为最终回答；即使原生两个 item 共用 ID，也保留不同事件身份。分享、仅消息导出和会话引用的文件读取路径沿用同一投影，并保留 review-only 回合的选择目录。

压缩只有已确认的 item 完成或成功结束的回合才能标为完成。缺少成功证据时，失败回合标为失败、中断回合标为停止，状态不明则保留未知。重建 writer 时恢复持久化压缩证据，已确认成功的压缩及其摘要、token 数不会被较弱的回合状态覆盖。

历史中相同的未知状态复用原生时间或已保存的首次观察时间，重读不产生新 revision。起始时间不可用时不伪造时间或计算耗时；实时完成采用原生通知的 `completedAtMs`。未知状态恢复运行时清除旧结束时间与耗时，临时中断更正为失败或成功时同步更新这些字段。内存活动淘汰后仍按 ID 读取持久化压缩证据。实时状态与历史重建采用相同规则。

## 后续独立能力

| 能力 | 接入前需要明确的语义 |
| --- | --- |
| 原生历史分叉 | 与现有携带摘要另开会话区分，保留原生历史与父子关系 |
| 对话上下文回退 | 与代码 checkpoint 恢复区分；操作前展示将移除的回合 |
| 原生持续目标 | 明确目标状态、预算、暂停及恢复，并接入原生状态事件 |
| 其他后端内置命令 | 逐项核验原生协议与执行回执；终端菜单可见不等于 RPC 可执行 |

## 验证边界

复用现有 Codex 协议夹具、transcript source 和真实 Store/Journal/Dispatcher 组合，覆盖回执顺序、竞争回合、停止与断线、单次副作用、权限配置、历史状态和重建后的结算。不新增 UI 展示测试，也不对真实用户会话执行压缩或 Review 来验证。

协议参考：[Codex App Server](https://learn.chatgpt.com/docs/app-server)。实施时同时核对本机 CLI 生成的 TypeScript 协议定义，避免直接依赖文档中的新版本字段。
